# Previewix: guide for coding agents

Previewix is a VS Code extension that replaces the built-in viewers for media and document files with richer custom editors. Clicking a file in the Explorer opens it in Previewix.

| File type | What Previewix provides |
| --- | --- |
| Video | Player, frame stepping with timecode, frame preview on the seek bar, subtitles (SRT, WebVTT, ASS text; files next to the video or tracks inside it), A–B loop, saving the marked range as a clip without re-encoding, saving a frame as PNG, media info panel (codec, bitrate, tracks), fullscreen |
| Audio | Player with waveform, stream details, tag and cover editor |
| Images | Zoom, pan, browsing the folder, crop (free or fixed ratio), rotate and flip, arrows, rectangles, ellipses, highlighter, text, blur and pixelate, color picker, metadata panel, export to PNG/JPEG/WebP at any size. Besides what Chromium decodes: HEIC/HEIF, TIFF (all pages), PSD/PSB (the flattened picture) and ICNS, and a choice among the sizes of an ICO or ICNS. A comparison of two images: side by side, blink, swipe, onion skin and the pixels that differ, with a tolerance; also against the committed version in Git |
| Markdown | Rendered view where each block is editable as source; math (KaTeX), Mermaid diagrams, footnotes, GitHub alerts, outline |
| HTML | The page as a browser shows the file, with the stylesheets, scripts and pictures next to it; live update from the source and from the files it loads; width presets; scripts on or off; links opened in VS Code |
| PDF | pdf.js viewer with find, outline, page thumbnails, zoom, rotation, dark pages; highlights, text notes, freehand drawing, pictures and form filling, saved into the file; export to Markdown |
| Word (.docx) | docx-preview rendering; export to Markdown |
| Fonts | Specimen with sample text, `@font-face` snippet, variable axes, OpenType feature switches, character grid by Unicode block, font details |
| SQLite | Table browser with paging, sorting and filtering; staged cell, row insert and delete edits; foreign keys followed both ways; table structure; SQL prompt for statements and scripts, with completion and a history per database; export to CSV/JSON, CSV import, blobs shown as pictures |
| CSV, TSV | Table with sorting, a row filter and a filter per column, cell selection with statistics (count, sum, average, min, max), copy as tab-separated text, Markdown, JSON or CSV; delimiter and encoding detection; editing of cells, rows and columns with undo, where a save rewrites only the fields that changed |
| Excel (.xlsx, .xls, .ods), Numbers | The same table per sheet, with values formatted as in Excel; export of a sheet to CSV |
| JSON Lines (.jsonl, .ndjson) | The same table with the keys as columns, nested values as JSON, broken lines reported |
| Parquet | The same table with the column types, read in a worker thread; the first million rows of a larger file |
| dBase (.dbf) | The same table with the field types, text in the code page of the file (or one chosen by hand), ISO dates, memo text from the `.dbt` / `.fpt` next to it, deleted records left out |
| Archives (ZIP family, 7z, RAR, tar and tar.gz/.bz2/.xz/.zst) | Tree of the content with sizes and dates, filter, opening a file from the archive, extraction of everything or a subtree, password-protected archives; "Compress to ZIP" in the Explorer |
| Animated GIF, WebP, APNG | Frame-by-frame player with a frame strip, speed, zoom, saving a frame as PNG |
| SVG | Rendered view with zoom, backgrounds, live update from the source, export to PNG |
| 3D models (glTF, GLB, STL, OBJ, PLY) | Orbit, pan and zoom, standard views, wireframe, grid, axes and backgrounds, glTF animations, Draco and meshopt compression, details panel, saving the view as PNG |
| Certificates (PEM, DER, PKCS #7) | Subject, issuer, validity with status, alternative names, key, fingerprints, usage and extensions of every certificate; chain order and who issued whom; certificate requests; keys described without being shown |

`README.md` is the user-facing description of every feature and shortcut. Keep it in sync when behavior changes.

## Commands

```sh
npm install
npm run typecheck   # tsc --noEmit over src/, then over test/
npm test            # the regression tests in test/, with node:test (see "The test suite")
npm run build       # esbuild: dist/extension.js, dist/sqliteWorker.js, dist/webview/*.js, dist/mermaid/, copies pdf.js, KaTeX and MediaInfo assets
npm run watch       # same, rebuilding on change
npm run package   # builds previewix-<version>.vsix (production, minified)
```

`F5` in VS Code runs the "Run Extension" launch configuration (builds first, then opens an Extension Development Host).

`npm test` runs the regression tests of the modules that work without VS Code (see "The test suite" under "Verifying changes"). There is no linter and no CI in the repository. `npm run typecheck` covers `src/` and `test/`; the webview scripts are plain JavaScript and are checked with `node --check media/<file>.js`.

The project is public on GitHub: https://github.com/fedorananin/previewix. A build is released by attaching its `.vsix` to a GitHub release tagged `v<version>` (`gh release create`). Commit, push and release only when the owner asks.

## Architecture

Every feature is a custom editor: a provider in `src/` that builds the webview HTML (inline template string in a private `html()` method), and a webview script that talks to it with `postMessage`. The one exception is the comparison of two images, a webview panel opened by a command (see "Comparing two images").

The handshake is the same everywhere: the webview posts `{ type: 'ready' }` once its script has loaded, and the provider answers with the data. Providers never push before `ready`.

Every provider calls `followFile()` (`util.ts`) and puts `missingAssets()` into the page's `<head>`:

- A change on disk goes to the provider's `onChange`.
- A file that disappeared is looked up by device and inode in its folder. If it is there under a new name, the editor is reopened on it with `vscode.openWith` and the old panel is closed (a background tab waits until it is visible). A rename made inside VS Code is handled by VS Code itself.
- Otherwise the webview gets `missing` `{name}`, and `media/missing.js` covers the page with a placeholder until `restored` arrives. The state is re-sent on every `ready`, because a page without `retainContextWhenHidden` is rebuilt when its tab comes back.
- `keep` suppresses both reactions: Markdown passes `document.isDirty` so unsaved text stays reachable, audio passes its `saving` flag.

All webviews use a strict Content Security Policy with a per-load nonce for scripts and no inline scripts or `eval`. Webview scripts start with `acquireVsCodeApi()` and keep small view state (playback position, zoom, scroll) with `vscode.setState`.

`package.json` registers each editor under `contributes.customEditors` with `"priority": "default"`, which is what makes it win over the built-in viewer. File extensions are listed in the `filenamePattern` globs there; upper-case variants must be listed explicitly.

### Video (`videoEditor.ts`, `subtitles.ts`, `videoTools.ts`, `media/video.js`)

- Messages to the webview: `source` (webview URI of the file), `info` (summary line, sections and `frameRate` from `mediaInfo.ts`), `tools` `{clip}` (whether ffmpeg was found), `subtitles` (`tracks` as `{id, label, detail, rev}`, `suggested`, and `select` after "Load subtitles…"), `cues` `{id, rev, vtt, language}` or `{id, error}`. From the webview: `ready`, `fullscreen` `{enter}`, `copy` `{text}`, `saveFrame` `{label, data}`, `subtitle` `{id}`, `pickSubtitles`, `saveClip` `{start, end, duration}` (a mark that isn't set is `null`).
- The detailed info panel is hidden by default. The whole bottom bar (`#bar`, a button with the centered summary line in it) toggles it, and the panel has its own close button next to Copy.
- Fullscreen: webviews can't use the HTML Fullscreen API, so the fallback toggles VS Code's Zen Mode (`workbench.action.toggleZenMode`), then un-centers the layout if `zenMode.centerLayout` is on. The webview infers whether Zen Mode is still active from its viewport height, because the user can leave it with VS Code's own shortcuts.
- The `<video>` has no native controls. `#controls` is an overlay inside `#stage` with play, seek bar, time, frame steps, save frame, the A–B marks, save clip, speed, loop, subtitles, volume and fullscreen; `updateControls()` mirrors the element's state into it, and it fades out (`#stage.idle`) after 2.5 s of playback without pointer movement. Because the overlay lives inside `#stage`, it stays available in fullscreen, where the bottom bar is hidden. Two-state buttons contain both SVG icons and CSS picks one from the state classes (`playing`, `muted`, `body.fs`).
- The bottom bar holds only the summary line, which starts with the file size.
- Frame stepping and the frame counter use `frameRate` from the `info` message (first video track). `stepFrame()` seeks to the middle of the neighbouring frame, so rounding can't land on the wrong one. The timecode is non-drop-frame.
- Saving a frame draws the `<video>` onto a canvas and posts `saveFrame` `{label, data}`; the provider owns the save dialog. Reading the canvas requires the video to be loaded with `crossorigin="anonymous"`. If the load fails with it, `video.js` retries without the attribute, and frame saving then reports that it isn't allowed.
- VS Code's Chromium lacks some decoders (AAC audio, often HEVC video). The webview detects a silent or pictureless track at runtime and shows a notice. There is deliberately no transcoding fallback; an earlier ffmpeg-based one was removed at the owner's request. Do not reintroduce it. What ffmpeg does for video (`videoTools.ts`) never feeds the player: it lists streams, copies packets into a clip, and reads the text of a subtitle stream.
- The audio notice counts what was actually played (`video.played`), not the position: a restored or sought-to position has decoded no sound yet.
- Shortcuts go through `shortcutKey()`, which falls back to the key's position (`e.code`) when the layout puts a non-Latin letter on it.
- The buttons wrap onto a second row in a narrow tab. A `ResizeObserver` keeps the height of `#controls` in `--controls` on `#stage`, which is what the subtitles are placed by.
- Subtitles:
  - `subtitles.ts` (no `vscode` import) does three things. `findSidecars()` picks the files of the folder that continue the video's name (`movie.srt`, `movie.en.srt`); a file that continues another video's name further belongs to that one. `decodeSubtitles()` reads UTF-8 and UTF-16 (by BOM, and UTF-16 without one by its zero bytes); what is left is an old code page, chosen by the language tag of the file name (`CODE_PAGES`) or, without one, between Windows-1251 and Windows-1252 by `looksCyrillic()`. `toWebVtt()` tells the format from the content and converts SubRip and ASS/SSA; WebVTT passes through untouched.
  - The SubRip parser is lenient on purpose: a cue runs from one timing line to the next, and the counter of the following cue is taken off its end, so missing counters, empty lines inside a cue and a missing final newline all work. `{\an7}` to `{\an9}` become `line:0`.
  - The provider lists the tracks (`subtitles`), the page asks for one by `id` (`subtitle`), and the provider answers with WebVTT text (`cues`). The page never names a file: files from "Load subtitles…" are kept in the provider (`picked`) for the life of the tab. `rev` (mtime and size) changes when a file does, which makes the page ask again; a watcher on the folder re-sends the list.
  - The page loads the text into a `<track>` through a blob URL (covered by `media-src blob:`) and sets its mode to `hidden`: the browser parses and times the cues, and `renderCues()` draws `activeCues` into `#subs` (or `#subsTop` for cues with a line near the top) from `getCueAsHTML()`, so no markup of the file reaches the page. The browser's own rendering can't be kept clear of the controls overlay, which is why it isn't used. Other cue settings (position, align, regions) and `STYLE` blocks are ignored.
  - `subChoice` in the page state is a track id, `'off'`, or undefined, in which case the provider's `suggested` track is shown (the file named exactly like the video, else one in `vscode.env.language`, else the first sidecar). Tracks inside the file are never switched on by themselves.
  - With ffmpeg, text subtitle streams inside the file (`textSubtitles()`: SubRip, ASS, mov_text, WebVTT) are offered as `stream:<index>` and read with `-f webvtt` when chosen, which may mean reading through the whole file; the result is kept per stream until the file changes. The list of sidecars is sent first and again with these once ffmpeg has answered.
- Seek preview: a second, detached `<video>` on the same source that is only ever sought (`peekSource()`), created on the first hover and released 20 s after the last. The timeline is cut into 240 slots that share a picture; pictures are small canvases in an LRU of 120; a seek starts 90 ms after the pointer came to rest and only one runs at a time. Chromium has no `fastSeek()`, so every seek decodes from the previous keyframe, and these limits are what keeps that affordable. Nothing is created when the player has no picture (`videoWidth` 0); the time label still shows.
- A–B loop: `markA` and `markB` in seconds, `null` when unset; one mark alone stands with that end of the video. `checkLoop()` runs on every animation frame during playback (and on `timeupdate`, for a covered window) and jumps back only when playback crosses the end mark, not after a seek past it. While marks are set, `video.loop` is off and the loop button's state lives in `loopOn`, because the element's own loop always returns to 0.
- Save clip (`saveClip()` in the provider, `cutClip()` in `videoTools.ts`):
  - `keyframesAround()` lists the packets around the start mark as a stream copy into ffmpeg's `framecrc` muxer with `-copyts`, which gives the time, size and checksum of the keyframes without decoding. `clipStarts()` decides: a mark on a keyframe's own frame starts there; otherwise the user picks the keyframe before or after in a QuickPick, before the save dialog. The closing message repeats the range the clip covers and names streams the container refused.
  - The cut is `-ss <keyframe> -t <length> -i file -map 0 -c copy` with `-copypriorss:<n> 0` on every video, audio and subtitle stream. That flag is what makes the result exact: an input seek lands on a keyframe that may be earlier than the one asked for (Matroska goes back up to 30 s for the sake of subtitle tracks) and on audio from before it, and the flag drops everything in front of the `-ss` time. It is not set for cover pictures and data tracks, whose single packet sits at the very beginning. `position()` rounds `-ss` down to the microsecond, since a start a hair after the keyframe would drop it.
  - `SELECTIONS` is tried in order when the container refuses the header: everything (`-map 0 -copy_unknown`), then video, audio and subtitles, then video and audio.
  - The clip is written to `tempSibling(target)`, then its first video packet is compared with the chosen keyframe's size and checksum, and only then renamed. The video itself is refused as a target (compared by device and inode). Formats without an index (MPEG-TS) may fail that check; they can't be marked in the player anyway, since Chromium doesn't play them.
  - Positions come from `video.currentTime` and go to ffmpeg relative to the file's start time, which `inspect()` reads from ffmpeg's description of the input (`parseStreams()`); the two agree for MP4 and Matroska files that start at zero.

### Audio (`audioEditor.ts`, `media/audio.js`)

- Messages to the webview: `source`, `info`, `tags` (fields, other tags, cover bytes, `writable`, `coverWritable`, optional `note`, `unavailable` when ffmpeg is needed and absent, which hides the tag section), `peaks` (waveform), `coverPicked`, `saved`, `saveError`. From the webview: `ready`, `pickCover`, `save` `{fields, cover: 'keep' | 'remove' | 'replace'}`, `copy`.
- The waveform comes from `readPeaks()` in `tags/ffmpeg.ts`, which decodes to 4 kHz mono through ffmpeg. Without ffmpeg the player simply has no waveform.
- The provider remembers the cover file picked in the open dialog (`pickedCover`) and applies it on the next `save`.
- A save replaces the file on disk, so the provider re-sends `source` with a cache-busting query and the webview restores the playback position. A `saving` flag stops the file watcher from treating the extension's own write as an external change.
- The webview is registered with `retainContextWhenHidden`, so unsaved tag edits survive tab switches and audio keeps playing in the background.

### Audio tags (`src/tags/`)

The editable fields are fixed: `FIELDS` in `tags/common.ts` (title, artist, album, album_artist, date, track, disc, genre, composer, comment, lyrics). Every backend maps its native names to these and returns `TagData { fields, other, cover }`, where `other` is shown read-only and must be preserved on save.

`tags/index.ts` dispatches by file extension:

| Format | Backend | Notes |
| --- | --- | --- |
| MP3 | `id3.ts`, native | ID3v2.3 and v2.4. Frames are kept as raw bytes; only frames behind a changed field are rebuilt, in the tag's own version and encoding rules. v2.2 tags are read through ffmpeg and are not writable. The ID3v1 trailer is dropped on save. |
| FLAC | `flac.ts`, native | Rewrites the metadata blocks in front of the audio frames. Multi-valued comments are shown joined with `; ` and left untouched unless the field changes. |
| WAV | `wav.ts`, native | Reads and writes both the `LIST INFO` chunk (seven basic fields) and an `id3 ` chunk (full ID3 tag via `id3.ts`, cover included). ID3 wins on read. RF64 is not supported. |
| M4A, M4B | `mp4.ts`, native | The iTunes item list in `moov/udta/meta/ilst`; see "MP4" below. A file it declines goes to `ffmpeg.ts`, a damaged one stays read-only. |
| Ogg, Opus, AIFF | `ffmpeg.ts` | Remux with `-c copy`, tags passed as an ffmetadata file. Requires ffmpeg. |
| Anything else | `ffmpeg.ts`, read-only | |

Rules that must hold for any change here:

- Audio data is never re-encoded or altered. Native backends copy the audio byte range; the ffmpeg backend compares an MD5 of the audio packets before and after and refuses to replace the file on a mismatch.
- The new file is assembled next to the original (`tempSibling()`), then renamed over it (`replaceFile()` for in-memory results, `rewriteFile()` for streamed byte ranges). Never write into the original in place.
- "Remove cover" removes every picture; "replace" swaps only the cover picture.
- A writer refuses a file it cannot account for, before anything is written. A file that ends inside its metadata (a FLAC block, an ID3 tag, a WAV chunk other than `data`) throws `Incomplete` from the reader and the writer; `index.ts` shows it read-only with that message and does not hand it to ffmpeg. The MP4 writer has `Mp4Refusal` for the same purpose.

Known ffmpeg quirks that shaped the design, verified against ffmpeg 8:

- Its MP3 muxer writes `comment` and lyrics as `TXXX` frames instead of `COMM`/`USLT`, and its FLAC and Ogg muxers rewrite `COMMENT` as `DESCRIPTION`. That is why MP3 and FLAC have native writers. Ogg and Opus still have this limitation.
- Ogg tags live on the audio stream, so they are read with `-map_metadata 0:s:a:0`, and written as global metadata with `-map_metadata:s:a:0 -1`.
- ffmpeg can't mux a picture stream into Ogg. The cover is passed as a `METADATA_BLOCK_PICTURE` tag built by `flacPicture()`.
- Its MP4 muxer (checked with ffmpeg 9) keeps only the tags it has names for: a remux drops freeform (`----`) atoms such as `iTunNORM` and `iTunSMPB`, sort names, BPM, rating and purchase data, and writes its own edit list, so the decoded length can differ by the encoder delay although the packets are identical. That is why MP4 has a native writer, and it is what still happens to the files that writer declines.

#### MP4 (`mp4.ts`)

- `load()` reads the top-level atoms (headers only) and the whole of `moov`, and returns the layout plus the reason the file can't be rewritten, if there is one. `Mp4Refusal` has three kinds. `foreign` (no `ftyp` at the start) and `unsupported` leave the file to ffmpeg, as before the native backend existed; without ffmpeg an `unsupported` file is shown read-only with the reason. `damaged` is read-only with or without ffmpeg. `index.ts` (`mp4Report()`, `saveTags()`) makes that choice. A refusal is always thrown before anything is written.
- Never guess on a write. Refused as `unsupported`: fragmented files (`moof`, `sidx`, `mvex`), a top-level atom other than `ftyp`, `moov`, `mdat`, `free`, `skip`, `wide`, data behind the last atom, more than one `moov`, `udta`, `meta` or `ilst`, QuickTime metadata (a `keys` atom, a handler other than `mdir`, a `meta` directly in `moov`), a compressed `moov`, a track without exactly one `stco` or `co64`, with a data reference outside the file, with an `iloc`, or with anything in `stbl` that is not on the `SAMPLE_TABLE` list (`saio` holds file offsets too), and a chunk that lies outside every `mdat`. Refused as `damaged`: an atom that ends behind the file, sizes inside `moov` that don't add up, no `moov`, and a chunk that ends behind the file. The size of every chunk is computed from `stsc` and `stsz`/`stz2` (`chunkLengths()`), which is what catches a cut file whose `mdat` has size 0 ("to the end of the file").
- Items are kept as raw bytes (`Item.raw`), and `editItems()` rebuilds only the ones behind a field whose value changed (`sameValue()` ignores line ends and outer spaces, which the form normalises, and compares track and disc as numbers). So everything else in the list is preserved byte for byte, and a save that changes nothing writes nothing. The genre is read from `©gen` or from the numeric `gnre` (ID3v1 list plus one) and always written as `©gen`. Track and disc are binary number/total pairs; text that isn't one is an error. A field stored as several `data` atoms is shown joined with `; `. The cover is the first picture of the first `covr` item; replacing swaps that one `data` atom, removing drops every `covr`.
- `moov` usually sits in front of `mdat` and addresses the audio by absolute file offsets, so `plan()` tries three things in order: (1) the `free` atom right behind `ilst` takes the difference and `moov` keeps its size; (2) a top-level `free` right behind `moov` takes it (the iTunes layout); (3) everything behind `moov` moves and `relocate()` adds the shift to every chunk offset at or behind the old end of `moov`, in every track (audio, chapter text, anything). A `stco` table that can't hold a moved offset is rebuilt as `co64`, which moves the audio further, hence the loop. Case 3 leaves 2048 bytes of padding so that later edits are case 1. Padding may grow to 64 KB (a smaller cover) before a save reclaims it through case 3.
- A missing `udta`, `meta` (as a full box, with an `mdir` handler) or `ilst` is created by `withList()`. A `meta` without version and flags (QuickTime form) is detected by which of the two readings gives a clean list of atoms, and stays in its form. A `udta` may end in four zero bytes; a new `meta` goes in front of them.
- `verify()` runs on the assembled file before the rename (the `check` argument of `rewriteFile()`): it must load without a refusal and have the expected size, the fields and pictures must read back as requested, every other item must be the same bytes, every `mdat` must have its old size at its expected place, every chunk offset must be the old one plus the shift, and the start, middle and end of a spread of chunks must be the same bytes through the old and the new table. A failure leaves the original untouched.

### Images (`imageEditor.ts`, `imageMeta.ts`, `media/image.js`)

- `resolveCustomEditor` only routes: a GIF, PNG or WebP that `isAnimated()` (see "Animated images") goes to `resolveAnimation()`, everything else to `showEditor()`, which sets up the editor.
- The provider sends the file bytes in an `init` message instead of a URL. A cross-origin image would taint the canvas and make export impossible. The page turns them into pixels with `previewixImages.decode()` (see "Image decoding"), whatever the format.
- Messages to the webview: `init` (name, ext, mime, bytes, `infoOpen`), `meta` `{sections, hasPlace}`, `folder` `{index, count}`, `saved`, `changed`, `error`, `page` `{index}`, `diff` `{paired}`. From the webview: `ready`, `save`, `copy` `{text, what}`, `openMap`, `navigate` `{delta, dirty}`, `infoOpen` `{open}`, `page` `{index}`, `compare`. `diff` and `compare` belong to `joinImageEditor()` in `imageCompare.ts`, which listens on the same webview (see "Comparing two images").
- A file with several pictures (sizes of an ICO or ICNS, pages of a TIFF, the rare HEIF with more than one) gets the `#pages` select; `Page Up` / `Page Down` step through it. `showPage()` decodes the chosen one and starts the editor afresh on it: annotations and undo history belong to one picture. With unexported edits the page asks the provider first (`page`), which shows the modal question and answers `page`. The index is kept with `vscode.setState` and survives a reload after a change on disk.
- `showPage()` is the only place a picture arrives. A newer call aborts the one before (an `AbortController`, which ends the worker), so a slow decode can't overwrite a newer picture. The old picture stays for 200 ms and is then replaced by "Decoding HEIC…" with a running bar; a decode that fails empties the editor and shows the decoder's message, with the select still usable.
- What the decoder did to the picture (profile converted, 16 bits reduced to 8, CMYK approximated, which decoder) comes back as `notes` and is shown in the info panel under "On screen", after the provider's sections; a `warning` is also shown as a toast.
- State in the webview: `base` (the current raster as a canvas, replaced rather than mutated, which keeps undo snapshots cheap), `items` (arrows, texts, `rect`, `ellipse` and `marker` strokes in image coordinates), `view` (scale and offset), `crop`, `cropRatio`, and `stateId`/`cleanId`, which say whether there are unexported edits.
- Annotations stay vector objects until export. `compose()` flattens them at the requested size, halving in steps for quality. A `marker` keeps its `points` array immutable (moves and resizes replace it), since snapshots copy items shallowly.
- Every geometric change goes through `mapItem()`: crop shifts, quarter turns and mirrors (`transform()`, `TRANSFORMS`) map the item's points, and boxes stay boxes. Texts are not turned or mirrored; they keep reading upright and follow their center. A quarter turn also turns the crop frame and the ratio lock.
- Blur and pixelate write a new `base`. The block size scales with the image (`blockSize()`: max(16, longest side / 80) × strength factor), because the tools exist to hide data and must stay irreversible on large screenshots too. `mosaic()` averages the blocks and adds slight noise; blur averages first and then applies a Gaussian over an edge-padded copy of the area, so nothing bleeds in or fades at the rim.
- The status color is sampled by composing just one pixel (`sampleAt()`), raster plus annotations, on each pointer move. The eyedropper copies it through the provider (`vscode.env.clipboard`).
- Image info: `imageMeta.ts` reads the container header itself (dimensions, bit depth, color type, DPI, PNG text chunks, WebP EXIF/ICC chunks; for TIFF, PSD, ICNS, ICO and HEIF through the readers in `imageFormats/`, so the panel lists the same sizes and pages as the select) and the tags with exifr (EXIF, GPS, XMP, IPTC, ICC); it has no `vscode` import. Dimensions follow the EXIF orientation, as the decoded picture does. HEIF and AVIF are the exception: there the container turns the picture (`irot`, `imir`) and every decoder, Chromium's included, ignores the EXIF tag, so `readHeif()` supplies the orientation and the final size; the row uses EXIF's words for it ("Mirror horizontal and rotate 270 CW"). PNG texts are read from `tEXt`, `zTXt` and `iTXt`, packed or not; a packed chunk is unpacked only for the keywords the panel shows and only up to `MAX_TEXT` (1 MB), since a few bytes can inflate to gigabytes. The EXIF block of a PSD is handed to exifr on its own, as for WebP. The coordinates stay in the provider, which builds the OpenStreetMap link itself. Whether the panel is open is kept in the provider, so it stays open while browsing.
- Browsing: the provider lists the folder on every step (`listImages()`: png, jpg, jpeg, jpe, webp, bmp, avif, ico, gif, svg, heic, heif, tif, tiff, psd, psb, icns; numeric-aware, case-insensitive), wraps around at the ends, asks with a modal dialog when the page reports unexported edits, opens the neighbour with `vscode.open` in the same view column (as a preview when the current tab is one), and disposes the current panel.
- Export: the webview encodes with `canvas.toBlob`, sends base64 in a `save` message, and the provider shows the save dialog and writes the file. The original is never overwritten implicitly, and metadata is not carried over.
- Crop with a locked ratio goes through `setCropFromAnchor()` (new frame, corner handles) and `setCropFromEdge()` (edge handles); both keep the frame inside the image without breaking the ratio. `cropPixels()` rounds so that the ratio survives pixel snapping.
- The toolbar uses inline-SVG icon buttons in groups and wraps onto a second row below about 850 px. Tool-specific controls (line width, font, outline, strength) float over the stage in `#toolOptions`, like the crop bar, so they don't widen the toolbar.

### Image decoding (`src/imageFormats/`, `webview/imageDecode.js`, `webview/imageWorker.js`, `webview/heicWorker.js`)

The piece that turns the bytes of any supported image file into pixels. It belongs to no page in particular: the image editor uses it, and any other page that shows pictures can.

- Interface: `previewixImages.decode(bytes, { page?, mime?, signal?, onBusy? })` resolves to `{ bitmap, format, pages, page, notes, warning? }`.
  - `bitmap` is an `ImageBitmap`, upright (orientation applied) and tagged with its color space, so drawing it on a canvas gives sRGB. The caller closes it.
  - `pages` lists the pictures in the file as `{label, width, height}` (always at least one) and `page` says which was decoded; pass `page` to get another. The default is the largest size of an icon that can be decoded, the first page of a TIFF, the primary picture of a HEIF.
  - `notes` are `[label, text]` rows about what was done to the picture; `warning` is something the user has to know before trusting the colors.
  - A failure rejects with an `Error` whose message is written for the user; an aborted `signal` rejects with its reason. When one picture of several can't be decoded, the error carries `pages` and `page` like a result, so the others can still be offered.
  - `previewixImages.formatOf(bytes)` names the format ("HEIC", "TIFF", …, "image" when unknown).
- To use it, a page loads `dist/webview/imageDecode.js` as `<script type="module" nonce=…>` in front of its own script, which then needs `defer` to keep running after it. The policy needs `script-src … 'wasm-unsafe-eval'`, `worker-src blob:` and `connect-src ${webview.cspSource}`, and `localResourceRoots` needs `dist/`. The script finds its workers and libheif relative to its own URL.
- The format is told from the content (`sniffFormat()`), never from the extension. An ISO media file with an `avif` or `avis` brand goes to Chromium, any other to libheif.
- Where each format is decoded:
  - PNG, JPEG, WebP, BMP, AVIF, GIF: `createImageBitmap` on the page.
  - ICO: `listIco()` reads the directory, and `icoPicture()` hands Chromium either the PNG of the entry or an icon file with that single entry, which leaves it nothing to choose. There is no bitmap decoder of our own.
  - ICNS: `listIcns()` walks the entries, the nested `dark`, `template` and `selected` variants included. A PNG entry goes to Chromium; the packed kinds are decoded on the page (they are at most 128 px): `ARGB` (`ic04`, `ic05`, `icsb`) and RGB planes with an 8-bit mask entry or, failing that, the 1-bit mask of the classic icon (`is32`, `il32`, `ih32`, `it32`). The run-length stream runs across the channels in ARGB, so it is unpacked as one. ARGB is straight alpha, as the PNG of the same size in the same file shows; `iconutil` extracts it as if it were premultiplied. JPEG 2000 entries are listed and refused.
  - TIFF and PSD: `imageWorker.js`, a web worker. HEIC: `heicWorker.js`, a web worker with libheif.
- A worker can't be started from the extension's files, so its code is fetched and started from a blob, as for pdf.js. Every decode gets a worker of its own that is terminated afterwards: that returns the decoder's memory (libheif's heap never shrinks) and is what stops a decode nobody waits for. The file bytes are copied to the worker, since the page needs them again for another page of the file. The worker makes the `ImageBitmap` itself and transfers it.
- Every worker decode has a deadline on the page (`PATIENCE` in `imageDecode.js`): 30 s for the worker to say how large the picture is (`{size}`, posted before the slow part), then 15 s plus a second per megapixel, about twenty times what the slowest decoder needs. Past it the worker is terminated and the user is told. A decoder caught in a damaged file can't be stopped from inside its own thread, so this is the one bound that holds whatever a decoder does; the bounds inside the decoders (below) are what keeps a damaged file from ever getting there.
- libheif (with libde265 inside) is LGPL-3.0, everything else here is permissive. Keep it out of every bundle: `copyAssets()` copies the library's own `libheif.js`, `libheif.wasm` and `LICENSE` unchanged into `dist/libheif/`, the page fetches the script and puts it in front of the worker code in the blob (it defines `libheif`), and the binary travels with the request as `wasmBinary`. Our code uses only its C API (`_heif_*` with `_malloc` and the heap views), declared in `heicDecode.ts`. The decoder runs in a webview worker whose policy allows no network beyond the extension's own files. `libheif-js` is pinned to an exact version in `package.json`, without a caret: its WebAssembly is a prebuilt binary, so a release is taken only after it has been out for a while, and the HEIC checks are rerun against it (decoding every fixture with the old and the new binary and comparing the pixels byte for byte shows at once what a release changes).
- A decoder in `imageFormats/` returns a `Raster`: straight RGBA, 8 bits, top row first, with the file's ICC profile (`icc`) or a named space (`colorSpace: 'display-p3'`, from HEIF code points) when the values are not sRGB. It throws `DecodeError` for everything it refuses on purpose; that message reaches the user as it is. `checkSize()` refuses what a canvas can't hold before anything is allocated.
- Color: the canvas is sRGB, and nothing here converts colors by hand except CMYK and Lab. `imageDeliver.js` wraps a raster with an RGB profile as a BMP with the profile embedded (`bmpWithProfile()`: a version 5 header, masks in R, G, B, A order, so the pixels go in untouched) and lets `createImageBitmap` decode that: Chromium honors the profile there exactly as in a PNG. Display P3 by code points goes through `ImageData` with `colorSpace`. So a P3 HEIC, TIFF or PSD comes out the same as a P3 PNG does natively, checked against `sips --matchTo` sRGB. CMYK goes through the polynomial pdf.js uses (`cmykToSrgb()`), not the file's profile, and carries a warning; Lab is converted exactly (`labToSrgb()`); gray profiles are not applied.
- TIFF (`tiff.ts`, `tiffDecode.ts`): `listTiff()` is our own reader of the directories. It checks every offset and count against the file, stops at a loop in the chain, and says whether a page's strips and tiles lie inside the file. UTIF (`utif2`) is used for decompression only and is given just the tags `listTiff()` read (`CODEC_TAGS`), because its own directory reader follows whatever it finds and its `toRGBA8()` is wrong for several layouts. `decodeTiff()` turns the samples into RGBA itself, refuses every compression outside `COMPRESSIONS` (the ones compared with other decoders), unpacks separate planes as one-sample pictures and weaves them, un-multiplies associated alpha, and applies the orientation tag (`orient()`). An extra sample marked "unspecified" is not alpha (Photoshop writes saved selections that way); a fourth RGB sample without the tag is, as in libtiff.
  - A damaged or hostile TIFF has to end in a picture or a `DecodeError` within seconds and without gigabytes, and UTIF's unpackers don't see to that themselves. Each one is replaced or fenced in at the top of `tiffDecode.ts`, by assigning to the functions and tables UTIF looks up when it runs:
    - LZW is our own (`lzw.ts`, `unpackLzw()`). UTIF's follows whatever codes it reads and never returns for some streams (the six bytes `80 01 e0 70 38 08`). Ours can't run away: every pass consumes at least nine bits, an entry only points at an earlier one, and a code the table doesn't have ends the stream.
    - Deflate: `pako.inflateRaw` is replaced by one that stops at the size of the strip, since UTIF unpacks a stream whole and a megabyte of zeros is a gigabyte.
    - JPEG: the size in the strip's own frame header is held against the strip before UTIF's decoder allocates it.
    - Fax (CCITT RLE, Group 3 and 4): the loops can't be reached, so the code tables are wrapped in a `Proxy` that refuses a bit string longer than any code, the function that extends a row refuses a row longer than the picture is wide or made of more runs than it has pixels, and the function that writes a row ends the strip after its last row (a megabyte of 1 bits is a million valid white rows in Group 4). Without these the bit string and the row grow for as long as there is input.
  - Before anything is unpacked, the size the file claims is held against the data it brings (`EXPANSION`: the most one byte can unpack to per compression, and one bit per row for fax), and the size of a tile against the picture, so a few bytes can't ask for a gigabyte. Fax compression on anything but a 1-bit picture is refused.
  - LZW data that ends early or goes wrong, and Deflate data that runs past its strip, are shown as far as they go, with a `warning`; data that lies outside the file, and fax data that is not valid, are refused.
- PSD (`psd.ts`): only the flattened picture at the end of the file is read; `readPsd()` walks the sections in front of it. Resource 1057 says whether that picture is real ("Maximize Compatibility"), and the file is refused when it isn't. The first extra channel is transparency when the layer count is negative or a `Mt16`/`Mt32`/`Mtrn` block is there (16- and 32-bit files keep their layers in `Lr16`/`Lr32`), or when the file has no layers and more extra channels than named alpha channels; otherwise it is a saved selection and ignored, as in Photoshop. Photoshop stores such a picture blended with white, while macOS and ImageMagick write the same structure with straight or multiplied colors: `decodePsd()` tells from the pixels (no channel darker than 255 − alpha means white) and undoes only what was done. 32-bit pictures are linear and get the sRGB curve; their profile is then dropped.
- HEIC (`heicDecode.ts`): libheif applies rotation, mirroring and cropping; `decodeHeic()` asks for interleaved RGBA, copies it out of the heap and releases the image before anything else is allocated. Decoding warnings (libde265 conceals damaged data instead of failing) become the `warning`. A sequence file is shown through its still picture, or refused when it has none. Forcing libheif's bilinear chroma filter was tried and dropped: twice the memory for a difference at pixel level.
- Measured on a 48-megapixel picture in Chrome on an M-series Mac, as decode time and as the peak of the renderer's memory above where it stood before: HEIC 2.3 s (3.3 s with the machine busy) and 600 to 700 MB (libheif's heap peaks at 300 MB), LZW TIFF 1.2 s and about 1.3 GB (the 127 MB file twice, the samples, the pixels, the bitmap), PSD 0.5 s and about 1.3 GB, PNG 0.3 s and about 0.4 GB. iPhone photos: 12 megapixels 0.4 s, 24 megapixels 0.8 s. The page's own thread is blocked only for drawing the bitmap into `base`, up to 0.6 s at 48 megapixels, as for any format.
- `heif.ts` (`readHeif()`) is a box reader for the info panel only: brands, the primary item's size, turn, mirror, depth, profile or code points, and whether there is a movie track. `imir` axis 0 exchanges top and bottom and axis 1 left and right (the standard's wording; libheif, Apple and Chromium agree). The transformations apply in the order the item lists them, and a mirror before a turn is not the same as after it, so `orientation` is the whole chain reduced to the EXIF orientation (1 to 8) that does the same; `decode(file)` equals `orient(decode(the same picture untransformed), orientation)` byte for byte for all eight. `imageMeta.ts` shares `listIco()`, `listIcns()`, `listTiff()` and `readPsd()` with the decoders.

### Comparing two images (`imageCompare.ts`, `media/compare.js`, `media/compareWorker.js`)

- Not a custom editor: a webview panel (`previewix.imageCompare`) opened by commands, because it belongs to two files and to no file type. It is absent from `contributes.customEditors`, and so from "Choose File Types…". `registerImageCompare()` registers `previewix.compareImages` (two files from the Explorer, or whatever leads to two), `previewix.compareImageWith` (one file; asks for the other in a QuickPick of the committed version, images open in other tabs and "Choose a file…") and `previewix.compareImageWithHead`, plus the panel's serializer.
- A side is a URI, `file:` or a `git:` URI of the built-in Git extension (path of the file, and `{path, ref}` as JSON in the query). `readSource()` reads a commit, branch or tag through the extension's API (`getAPI(1)`, `getRepository()`, `repository.buffer(ref, path)`; never the git program), and everything else through `workspace.fs`, which for `git:` is the Git extension's own file system: only it knows that `~` means "the index, else HEAD" and `~1` to `~3` the stages of a merge. `gitApi()` answers `undefined` when the extension is missing or disabled, and every caller copes with that.
- Messages to the webview: `init` (`id`, `mode`, and per side `name`, `detail`, `tip`), `side` (`index`, and either `bytes`, `size`, `hash`, `animated` or `error`), `saved`. From the webview: `ready`, `mode` (the next comparison starts in the mode used last), `open` `{index}`, `save` `{data}`. The side numbers are the provider's; which of them is A is the page's business (`settings.swapped`).
- `followFile()` is made for one file per editor (it covers the page, and reopens the editor on a renamed file), so it is not used here, and `missingAssets()` isn't either. Each `file:` side has `watchFile()`, each `git:` side the repository's `state.onDidChange`, which fires on every status refresh. `sendSide()` therefore sends a side again only when its fingerprint (SHA-1 of the bytes, or the error text) changed. A file that is gone leaves its side with a message and the other picture on screen.
- The page keeps only an `id` in its state. The pair behind it is kept in `workspaceState` (`previewix.comparisons`, the last 30), so a restored tab (`onWebviewPanel:previewix.imageCompare` in `activationEvents`) finds its files without the page ever naming a file to read. The panel has no `retainContextWhenHidden`: a hidden tab gives its pictures back, and on return the page is rebuilt from the state (mode, tolerance, alignment, swap, and the view when the pictures have their old extent).
- The page decodes with `previewixImages.decode()` (see "Image decoding"), one picture after the other, since two decoders at once would double the peak of memory. The two `ImageBitmap`s are all the page holds of the pictures: they are drawn straight onto a canvas of the size of the stage, never copied into canvases of their own.
- Geometry: the plane is measured in pixels of A, whose corner is the origin; `layOut()` puts B on it by `settings.align` (a corner, the middle, a hand-set offset, or scaled to A's size). `overlap` is what both cover and the only part that is compared; `union` is what the view fits. Nothing is scaled unless the alignment says so, and `updateAlignment()` words whatever is not simply "one on the other" for the user.
- The comparison (`compare()`): the page reads both pictures in strips of 1.5 megapixels (a `willReadFrequently` canvas, `drawImage` with "copy", `getImageData`) and transfers the buffers to a worker, two strips under way at a time. No copy of a picture is ever made, and no step blocks the page for long. Sending the `ImageBitmap`s to the worker instead would clone them (192 MB each at 48 megapixels), and transferring them would leave the page without pictures.
- The worker (`compareWorker.js`, fetched and started from a blob, like the decoders) keeps one byte per pixel: the largest difference in red, green, blue or alpha, with colors weighted by alpha as on screen (so colors behind full transparency count for nothing). From that it keeps a histogram, which makes the count for any tolerance instant on the page, and a pyramid of halvings by maximum. `box` scans a coarse level and only the rim of the box at full size. `render` draws the marks of an area at a given size from the level that fits, so one pixel of the result is marked when any pixel under it differs. Zoomed out, the page asks for exactly the pixels of the screen (`wantMarks()`): drawn at any other size, a single mark could fall between two of them.
- A change of either picture, of the alignment or a swap ends the worker and starts another; that is also what frees its memory, and `endJob()` rejects whoever still waits for marks. A change of the tolerance only asks for a new `box` and new marks.
- Modes: `paint()` draws pictures of the plane into a pane under one view (`screen = pane + plane × scale + offset`). Side by side has two panes with the same view, which is all there is to "locked together"; they lie above each other when that shows the pictures 25% larger (`stacked()`). `settlePane()` keeps the middle in the middle when a pane changes its size, and runs when that happens, not when it is drawn.
- "Save difference" composes the compared area at full size on the page (A faded on white, then the marks strip by strip from the worker) and posts base64; the provider owns the dialog.
- Measured in headless Chrome on an M-series Mac with two pictures of 8000 × 6000: JPEG 0.45 s to decode each and 0.4 s to compare, the result on screen 1.3 s after the page loaded; HEIC 2.3 s each, 5.4 s in all; PNG (100 MB files) 1.6 s. The page's thread was never blocked for more than 80 ms. The renderer grew by 0.8 to 0.9 GB while loading and held 0.6 to 0.8 GB afterwards (384 MB are the two pictures, 64 MB the worker; the rest is Chromium's reduced copies for drawing them small). A new tolerance was answered in about 0.1 s; dragging ran at 60 frames a second in every mode. Saving the difference took 3 to 4 s, 0.5 to 0.8 s of them in one block, for a PNG of 80 to 100 MB.
- The image editor inside a diff editor (`joinImageEditor()`): a changed image clicked in Source Control opens VS Code's diff editor with one whole image editor per side, on a `git:` and a `file:` URI. The stable API has no hook for that and no way to ask "is this editor half of a diff": such a tab's `input` is unknown, not `TabInputCustom`. What it does report is both halves as `visible` in the same `viewColumn` at once, which two editors of an ordinary group never are, and that is the test (`partnerOf()`, taken 250 ms after the last view-state event, because the states of a tab switch arrive panel by panel). A pair gets `diff` `{paired: true}`: the page hides the editing groups (`body.in-diff`) behind **Compare**, which opens the comparison of the two halves, and **Tools**, which brings the toolbar back for good. Nothing depends on the answer being right: an unrecognised pair stays two ordinary editors, a wrong one costs a click on **Tools**. The same registry answers the editor's `compare` message and the button in the diff editor's title bar (`editor/title`, `activeEditor == workbench.editors.binaryResourceDiffEditor`). Animated images, which have a page of their own, are not part of it.
- VS Code 1.140 carries a proposed API for exactly this (`customEditorDiffs`: `resolveCustomEditorInlineDiff({original, modified}, panel)` on the provider, which would make the comparison page the diff editor itself). A published extension can't use proposed API, so nothing here does; it is the thing to move to once it is final.
- None of the VS Code side could be run from the harness: the menus and their `when` clauses, the QuickPick and dialogs, the real Git extension, the view states of a real diff editor, and the restore after a reload were written from the API documentation and from reading the code of VS Code 1.140 and its Git extension.

### Animated images (`animationView.ts`, `media/animation.js`)

- Not a custom editor of its own: `.png` and `.webp` are usually still images, so the image provider sniffs the bytes with `isAnimated()` and hands the panel to `resolveAnimation()`. The page runs under the `previewix.image` view type. The choice is made once, when the file is opened.
- `inspectAnimation()` walks the container (GIF blocks, PNG chunks, RIFF chunks) without decoding anything and returns format, size, the delay of every frame and the play count. "Animated" means more than one frame: a one-frame APNG or WebP stays with the image editor.
- Messages to the webview: `init` (`name`, `info`, file `bytes`), `error`, `saved`. From the webview: `ready`, `save` `{frame, data}`. A change on disk re-sends `init`; the page keeps its frame.
- Decoding is WebCodecs `ImageDecoder`, one `decode({frameIndex})` at a time through `pump()`. `nextJob()` decides what is worth decoding: the frame to show, then the next few for playback, then thumbnails in view.
- Decoded frames are `ImageBitmap`s in an LRU cache capped at 192 MB of RGBA (4 to 400 frames). The frame on screen is never evicted.
- Playback runs on `requestAnimationFrame` against a due time. Frames are never skipped; a late frame keeps the rhythm and a stall restarts the clock. Delays of 10 ms or less are played as 100 ms, as browsers do.
- The delays come from the container, so the duration and the scrubber are right before any frame is decoded. If the decoder finds a different frame count (a truncated file), delays are learned from `VideoFrame.duration` instead.
- The strip is virtual: `#stripInner` has the full width, and cells exist only for the range in view. Thumbnails are small canvases in their own LRU (800).
- Without `ImageDecoder`, or when decoding fails, `loadPlain()` shows the file in an `<img>` from a blob URL (the reason for `img-src blob:`): it plays, zoom works, and the frame tools are disabled with a notice.
- "Save frame" encodes in the webview and the provider owns the dialog, as in the image editor. "Copy frame" uses `navigator.clipboard.write` and is hidden when the API is missing.

### SVG (`svgEditor.ts`, `media/svg.js`)

- A `CustomReadonlyEditorProvider`. Messages to the webview: `svg` (`name`, `text`, `size`, `unsaved`), `error`, `copied`, `saved`. From the webview: `ready`, `openSource` `{beside}`, `copy`, `save` `{data}`.
- The text comes from a dirty `TextDocument` of the same URI when there is one, otherwise from disk (`decodeXml()` honours a BOM and the XML declaration). `onDidChangeTextDocument` and `onDidCloseTextDocument` re-send it on a 150 ms debounce, `followFile` on a disk change. A counter drops a read that finishes after a newer one.
- The SVG is only ever rendered as an image, never as inline markup: scripts don't run and outside references aren't fetched. The CSP is `default-src 'none'` plus `img-src data:`.
- It must be a `data:` URL, not a `blob:` one: Chromium taints a canvas after drawing an SVG with `<foreignObject>` from a blob URL, which would break PNG export.
- A `DOMParser` copy is used only for inspection: parse error, root element and namespace, size attributes, viewBox, element count. The policy also applies to that inert document, so the console may report refused inline styles; that is harmless.
- Size at 100%: absolute `width`/`height`, else the viewBox (Chromium alone would say 300 × 150). With neither, `measureContent()` rasterises the file small through a wide viewBox, finds the painted pixels, and repeats closer in; the picture is then shown through a viewBox around the drawing. "Copy SVG" always copies the unmodified text.
- Zoom resizes the `<img>` itself (`#sheet` gets a width and height, no transform), so Chromium redraws the vector picture at that size. Export draws the image onto a canvas at the target size, capped at 16384 px a side.
- Every update loads into a new `Image` and swaps it in once decoded, so typing in the source doesn't flicker. A broken file leaves the last good picture dimmed under the error. Zoom is kept across updates unless the size changes.
- `previewix.openSvgPreview` (button in the text editor's title bar) leads back from the source, like the Markdown command.

### 3D models (`modelEditor.ts`, `webview/model.js`)

- A `CustomReadonlyEditorProvider` for `.glb`, `.gltf`, `.stl`, `.obj` and `.ply`. The engine is three.js, bundled into `dist/webview/model.js` (about 740 KB minified: the core, `GLTFLoader`, `DRACOLoader`, `STLLoader`, `OBJLoader`, `MTLLoader`, `PLYLoader`, `OrbitControls`, `RoomEnvironment` and the meshopt decoder).
- Messages to the webview: `source` (`src`, `stamp`, `name`, `ext`, `size`, `textLimit`), `error`, `saved`. From the webview: `ready`, `openSource` `{beside}`, `copy` `{text}`, `save` `{data}`.
- The page fetches the file from its webview URI, and through it everything the file names: a `.gltf`'s buffers and textures, an `.obj`'s `.mtl` (found by its `mtllib` lines) and that one's textures. `localResourceRoots` are the model's folder and, when the file is in one, the workspace folder (for `../textures/…`).
- `loadContext()` gives every load one `LoadingManager`. It rewrites URLs (backslashes, a Windows absolute path cut down to its file name, the reload `stamp` against the cache), collects what failed, and knows when nothing is on its way any more (`settled()`). A file that can't be had becomes a line in the notice and under "Problems" and the rest is shown; only a missing glTF buffer is fatal.
- CSP: `connect-src` with the webview origin, `blob:` and `data:` (the model, its buffers and the Draco decoder are fetched, and so are glTF textures, which are decoded as bitmaps; embedded ones are blobs and data URIs); `img-src` with the webview origin alone, for `.mtl` textures, which go through `<img>`; `'wasm-unsafe-eval'` for the Draco and meshopt decoders; `worker-src blob:` because `DRACOLoader` runs its decoder in workers that it starts from a blob. No other origin is allowed, so a model can't make the page call a server: a remote URI is reported as not loaded.
- Draco: `esbuild.js` copies `draco_wasm_wrapper.js` and `draco_decoder.wasm` (three's glTF-only build) to `dist/model/draco/`. They are fetched only by a model that needs them, and the loader is disposed after each load, so no worker stays behind. Meshopt is a small WASM module inside the bundle.
- KTX2 (Basis Universal) textures are deliberately left out. The transcoder's Emscripten glue builds functions from strings, which needs `'unsafe-eval'`; under this policy its worker dies without a word and the load never ends. A plugin registered under `KHR_texture_basisu` answers for such textures instead: with the plain picture if the file carries one as well, otherwise with no texture and a note. Do not add `KTX2Loader` without solving that.
- Orientation: the scene is Y-up, as glTF is. `tilt` is a group that turns a Z-up file onto it; Z is the default for STL, Y for everything else, and the **Up** select overrides it per file. The bounding box in the details is in the file's own axes, and the axes helper sits inside `tilt` for the same reason.
- Light: `scene.environment` is a `RoomEnvironment` run through `PMREMGenerator` (no file needed) at half intensity, plus a directional light that is a child of the camera; neutral tone mapping. Without an environment a physically based material is black.
- Materials: a file without them gets `plainMaterial()` (matt grey, double-sided, vertex colours when present). `OBJLoader` and `MTLLoader` make Phong materials, which take no light from the environment, so `loadObj()` rebuilds them as `MeshStandardMaterial`, without the textures that did not arrive (they would be drawn black).
- Framing: `frame()` puts the camera where the eight corners of the bounding box just fit, seen from a given direction. The near and far planes follow the camera (`updateRange()`), which is what makes a model of a millimetre and one of a kilometre both work. Until the user moves the camera (`state.camera` is null) the model is framed again on every resize and reload; after that the camera is kept, across reloads as well.
- Rendering is on demand: `requestRender()` schedules one frame and nothing else draws. `OrbitControls` runs without damping for that reason. The only loop is a playing animation: `draw()` asks for the next frame while `playing`.
- Reload: the new model is loaded in full and then swapped in (`show()`), and the old one is given back with `dispose()` (geometries, materials, textures and their `ImageBitmap`s, skeletons). A file that fails leaves the last good model dimmed under the error.
- Context loss: `webglcontextlost` shows a message and stops the drawing. On `webglcontextrestored` three.js uploads the scene again by itself; the environment map is a render target and is made anew. Without WebGL `renderer` is null: the file is still parsed for the details, and the stage says why nothing is drawn.
- "Save PNG" draws the view once more at 1×, 2× or 4× the canvas (at most 8192 px and what the GPU allows) and reads the canvas in the same task, because the drawing buffer is not preserved. The scene's background repeats the computed background colour of `#stage`, so CSS decides it in one place and a theme switch is followed; on the checkerboard it is null and the PNG is transparent there.
- Limits (`MAX_BYTES` in the provider): 512 MB, and 128 MB for `.gltf` and `.obj`. A text STL or PLY is told from its content and held to the same `textLimit` in the page. Text costs 15 to 25 times its size in memory while it is parsed.
- State (`vscode.setState`): camera, up axis, wireframe, grid, axes, background, details panel, animation clip. The editor is registered without `retainContextWhenHidden`: a tab in the background holds nothing on the GPU and loads the file again when it comes back.
- `previewix.openModelPreview` (button in the text editor's title bar) leads back from the source of a `.gltf` or an `.obj`. Unlike the SVG view, the model follows the saved file, not the unsaved text.

### Certificates (`certEditor.ts`, `certInfo.ts`, `media/cert.js`)

- A `CustomReadonlyEditorProvider`. Messages to the webview: `file` (`name`, `size`, and the `CertFile` of `parseCertFile()`: `format`, `text`, `blocks`, `chain`, `notes`, `message`), `error` `{name, message}`. From the webview: `ready`, `openSource` `{beside}`, `copy` `{text, what}`.
- **Nothing of a private key reaches the webview.** The provider sends the description and never the file's bytes or text. `certInfo.ts` returns, for a private key, only its format, algorithm, size, how it is encrypted, and the hash of its public half. The challenge password of a request and the text around the PEM blocks are not passed on either (the password not inside a PEM either: such a request has none), and a block with an unknown label is passed as its label and size. Keep it that way: no "show the key" button, no raw text in a message.
  - `pem` (what "Copy PEM" copies) is the one place where bytes of the file go to the page, so it exists only for what was positively recognised as public, all of it (see "What is given back as PEM" in `certInfo.ts`). The readers tolerate damage and read past what they don't understand, and a private key can sit under any label and inside any wrapping, so "it began like a certificate" describes a block and never hands it back. There are two levels:
    - The skeleton, which decides whether a block is described as a certificate, request or CRL at all: every field that is there has the tag of its place (`startsLike()`, `inOrder()`); a field may be damaged inside or missing at a cut. An octet string where the issuer belongs means it is something else, and the block is "Unreadable".
    - `sound`, which `pem` and the fingerprints need: `intact()` (no element is cut, and the parts of every constructed element fill it exactly), all three signed parts, and every field of the form it must have (`isAlgorithm()`, `isName()`, `isValidity()`, `isSpki()`, `isExtensionList()`). A block that is whole but not sound says so in `problems`.
    - A request is also given back only when each of its attributes is in `REQUEST_ATTRIBUTES` or is the extension request. With a challenge password, or an attribute not known here (whose value is not shown), it has no `pem` and a note says why: the PEM is the whole request, and a request can't lose an attribute and keep its signature.
    - A public key must be whole and nothing but a key: `isSpki()`, or for PKCS #1 `isRsaPublicKey()` (two numbers that can be a modulus and a public exponent). It gets `pem` when its algorithm is one known here.
    - What the form can't tell stays possible: a secret written into a slot that is public by definition (a serial number, the "modulus" of a well-formed public key) is shown like any other value. No tool writes such files.
  - `readDer()` ends an element that runs past the data where the data ends, so a cut file looks like a smaller, complete structure. Anything told by its exact shape must therefore ask `intact()` first: `guessLabel()` names a public key, DH parameters or a two-number RSA key only when the file is whole, takes a cut run of numbers behind a version for the private key it is, and calls a file cut before the field that tells a version 1 certificate from a CRL neither. `privateKeyBlock()` reports a cut key as damaged and derives no size or hash from a number that is cut.
- Parsing is hand-written and does not use `crypto.X509Certificate`: VS Code's crypto is BoringSSL, which refuses some certificates and key types that OpenSSL reads, and what Node exposes changes between versions (`engines.vscode` goes back to Node 20). A small DER reader (`readDer()`, `kids()`) serves certificates, requests (PKCS #10), CRLs, PKCS #7 bundles, PKCS #1, PKCS #8 and SEC 1 keys, and the header of OpenSSH keys. `crypto` is used for three things: hashes, checking signatures, and deriving the public key of a private key that doesn't carry it (Ed25519).
  - `readDer()` clamps an element whose length runs past the data and marks it `cut`; `kids()` returns the children that can be read. Each part of a block is read inside `part()`, which turns a failure into a line in `problems`, so damage costs only the field it hits. A certificate that is cut, or not sound, has no fingerprints and no PEM.
  - BER indefinite lengths are followed, for PKCS #7 files, to a depth of 64.
- `verify()` answers `true`, `false` or `undefined` (this runtime can't tell). Under VS Code that is `undefined` for Ed448, DSA, secp256k1, Brainpool, explicit curve parameters and ML-DSA; RSA (with PKCS #1 and PSS padding), P-224 to P-521 and Ed25519 are checked. `plainRsa()` rewrites an RSA-PSS key as a plain RSA one, since BoringSSL reads only that.
- The public key hash of an RSA or EC private key is built by hand from the numbers in the key, so it is the same in every runtime and equals the hash of the certificate's key. Deriving it through `crypto` gave another encoding for explicit curve parameters under BoringSSL.
- `relate()` works out the relations after all blocks are read: an issuer is a certificate whose subject equals the issuer name (byte for byte, or ignoring case and spacing), whose key identifier doesn't contradict, and whose key verifies the signature; without a possible check the first candidate by name is taken and marked unchecked. Blocks with the same public key hash are linked. The certificates form a chain when they are one path, and `chain.state` says whether the file lists it leaf first (`ordered`), root first (`reversed`) or neither (`mixed`).
- A file is PEM when it contains a BEGIN line, otherwise DER when it starts with a sequence whose shape `guessLabel()` recognises, otherwise Base64 without armor. The label of a DER file is a guess: when the reader of that kind then refuses the content, the file is of no known kind (a message, no block), except that what looked like a private key is shown as a damaged one. `scanPem()` accepts CRLF, text between blocks, a missing END line, indentation, a single line and escaped `\n`; UTF-16 is decoded and noted, because other tools reject it.
- Limits: 16 MB (`MAX_BYTES`, checked by the provider before reading) and 1,000 blocks.
- The page: one card per block, built on first unfolding (a trust bundle has over a hundred). Everything that depends on the clock is computed in the webview from `validity` (`statusOf()`), and `renderStatus()` runs again every minute. The report for the clipboard is built from the same sections. Names from the file go into the page with `textContent` only.
- "Open source" is shown for a file that reads as text, and for a file in which nothing was recognised, as the way out. `previewix.openCertPreview` (button in the text editor's title bar) leads back, and is also offered on `.key` files, which the editor does not claim.
- Unsaved edits in a text editor are not followed, unlike SVG: the page shows the file on disk.

### Markdown (`markdownEditor.ts`, `markdownRender.ts`, `markdownEdit.ts`, `media/markdown.js`)

This is a `CustomTextEditorProvider`, so the document is a normal VS Code `TextDocument`: dirty state, save, auto save and hot exit come for free.

- Rendering happens in the extension host. `renderDocument()` returns one entry per top-level block with its source line range `[start, end)` and HTML, plus the outline (top-level headings with level, text and id). Front matter is cut off and rendered as its own block. The whole document is rendered on every change, and the page then builds every block element anew.
- Editing is per block, by design. A block edit rewrites only that block's lines (`planEdit()`), so the rest of the file stays byte-for-byte intact. A WYSIWYG round trip that reformats the whole file was rejected for this reason.
- Sync protocol: the webview sends `edit` `{version, start, end, text, remove}` one at a time. The provider rejects an edit whose `version` isn't the document's current version (`rejected`), otherwise applies it and answers `applied` with the block's new line range. Every document change produces an `update` (lines, blocks, outline, version, and `own` + `range` when it was this editor's own edit).
- While a block is open, its text is synced on a 200 ms debounce. If an external change alters the block's lines, the editor is closed with a notice.
- Task-list checkboxes carry `data-line`; clicking one flips `[ ]`/`[x]` on that line (`toggleTask()`).
- `markdownRender.ts` and `markdownEdit.ts` have no `vscode` import on purpose, so they can be exercised outside VS Code.
- "Open source" opens the text editor in the same editor group. The `previewix.openMarkdownPreview` command (button in the text editor's title bar) goes back.
- The Markdown extensions are rules written in `markdownRender.ts` rather than plugins, because each has to fit the block model:
  - Math: an inline rule for `$…$`, `$$…$$` and GitHub's ``$`…`$``, and a block rule for `$$` lines, which makes a formula with blank lines in it one block. A `$$` that is never closed is not math, or it would swallow the rest of the document. A single `$` opens only before a non-space and not after a letter or digit, and the next `$` has to close it (after a non-space, not before a letter or digit); that is what keeps `$5 and $10` text. KaTeX renders to HTML in the host (`renderMath()`, cached, since nearly every formula is the same on the next render) with `throwOnError`, and the catch writes the source and the message in place. `trust` stays off.
  - Footnotes: a definition is not moved to the end of the page, as footnote plugins do. It stays a top-level block where it is written (`footnote_open` carries the `map`), so it is edited like any other. Block parsing registers the labels, inline parsing numbers them in the order of the first reference, and a core rule then adds the back links, one per reference. A reference without a definition stays text. A definition without a reference, or with a label that is taken, is shown dimmed instead of hidden, because a block that isn't on the page can't be edited.
  - Alerts: a core rule turns a quote whose first line is `[!NOTE]` (and so on) into `<div class="alert alert-note">` with a title line.
  - Heading ids are GitHub's (lower case, punctuation dropped, a hyphen per space, `-1`, `-2` for repeats), made from the heading's text without its markup.
  - A `mermaid` fence leaves the host as `<div class="diagram"><pre><code>source</code></pre></div>`, a `math` fence as a formula.
- Ids from the document must not land on the page's own elements: a heading "Outline" would take the styles of `#outline`, and "Missing" those of the placeholder. `blockElement()` moves an id that is in `taken` to `data-id`, and links and the outline are resolved by `findAnchor()`, inside `#content` only.
- Mermaid (`webview/mermaid.js`, and `hydrate()` with what follows it in `media/markdown.js`):
  - It needs a DOM, so it runs in the page. `esbuild.js` builds it into `dist/mermaid/` with code splitting (about 100 chunks, 3.4 MB). The page imports `mermaid.js` with `import()` when the first diagram turns up, and Mermaid imports the chunk of a diagram type when one is drawn. The nonce of the page's script covers what that script imports, so `script-src` stays `'nonce-…'`.
  - `securityLevel: 'strict'`. A diagram can choose a theme with a directive, but not the security level.
  - Mermaid is pinned to 11.17.2 and KaTeX to 0.18.9, as exact versions. Mermaid stays on the 11 line on purpose: 12 bundles elkjs (1.5 MB, EPL-2.0) and makes ELK the default layout, and 12.0.0 carries a `lodash-es` with known advisories. Mermaid 11 has no ELK in it and draws a diagram that asks for it with dagre. The build fails if elkjs turns up in the bundle, so that moving to 12 is a decision about that licence and not a version bump.
  - Pictures are kept in `drawn` by theme and source, as elements that are moved into the new block when the page is built again, so a change elsewhere in the document costs nothing and nothing flickers. `shown` remembers the last good picture of each diagram, known by the first line of its block, which doesn't change while the block is edited. That picture stays while a changed source is being drawn, and in the editor's preview it stays dimmed under the message while the source is wrong, which is the usual state of a diagram that is being typed. Outside the editor a wrong diagram shows its source and the message.
  - No jumping: the size of each diagram is kept in the webview state by a hash of its source (`sizes`; for a failed one, the height of its box). When the tab comes back, `reserve()` gives every diagram its place before Mermaid has loaded, so the scroll position is restored once and holds. `.diagram` is a flow root so that it is as tall with a picture as with the placeholder.
  - Mermaid lays a picture out in `#stage`: hidden, as wide as the diagram's box, and a `.block`, so that labels are measured in the styles they will be shown in.
  - Theme: `diagramLook()` gives `default` for light and `dark` for dark themes, and for high contrast a `base` theme made of the editor's background, foreground and contrast border. A `MutationObserver` on the classes of `<body>` and the style of `<html>` calls `hydrate()` again.
- CSP: `style-src … 'unsafe-inline'` was there already for raw HTML in documents, and both libraries need it: KaTeX sizes everything with `style` attributes, and Mermaid puts a `<style>` element into each SVG. `font-src` for the KaTeX fonts is the only addition. `dist/katex/` holds KaTeX's stylesheet and its `.woff2` fonts, the one format Chromium takes from that stylesheet.
- Outline: `#outline` is a fixed column under the bar, and `html.with-outline` pushes the document aside (below 720 px it lies over the document). The mark is the last heading above a line just under the bar, found by halving; at the end of the document the line is the bottom of the window. Whether the outline is open is kept in the webview state and, as the default for documents opened later, in global state (`markdown.outline`; the page sends `outline` `{open}` and gets the default as `data-outline`).

### HTML (`htmlEditor.ts`, `htmlPage.ts`, `media/html.js`)

- A `CustomReadonlyEditorProvider`. Messages to the webview: `page` (`name`, `size`, `unsaved`, `empty`, `scripts`, `force`, `html`, `own`, `browser`), `error`, `note` `{text}`. From the webview: `ready`, `openSource` `{beside}`, `openBrowser`, `scripts` `{on}`, `link` `{href}`, `resources` `{urls}`.
- The text comes from a dirty `TextDocument` of the same URI when there is one, otherwise from disk, as in the SVG view; changes are re-sent on a 300 ms debounce. `decodeHtml()` follows a browser: byte order mark, the charset declared in the first 1024 bytes, UTF-8, and Windows-1252 when the bytes are not valid UTF-8.
- The webview page is the toolbar, and the file is written into an `<iframe>` inside it (`load()`, `write()` in `html.js`) with `document.open()`, `write()`, `close()`. How that frame is made is the one thing here that leans on VS Code's insides:
  - VS Code serves a webview's files through a service worker, which finds the webview of a request by the `id` in the address the requesting frame was loaded from (`getWebviewIdForClient()` in VS Code's `webview/browser/pre/service-worker.js`). A frame made from `srcdoc` or a blob has no such address and gets 404 for every file next to the page. So the frame is loaded from `./fake.html?id=…`, exactly as VS Code loads its own frame (`pre/index.html`), and then written into. `ADDRESS` takes the id from the page's own navigation entry, and falls back to `about:blank` where there is none (a test page).
  - Checked against the sources and a running VS Code 1.140. If a later VS Code changes that scheme, the page still shows but without its stylesheets and pictures: read those two files of VS Code again first.
  - After `document.open()` the frame's document has the address of the webview page, not of the file. `location.reload()` therefore loads VS Code's webview host page into the frame (`left()` notices and writes the file again), and `history.pushState()` with a relative address throws, since the `<base>` is another origin.
- `preparePage()` puts two things at the start of the head (`headStart()`: behind the doctype, `<html>` and `<head>`, never in front of the doctype, which would mean quirks mode): the policy of the page (`pagePolicy()`) and a `<base>` on the folder's webview address. A `<base>` of the page's own is resolved against the folder and takes part in the one written first (`baseOf()`). A policy of the page's own gets the folder's origin named beside `'self'`, which would otherwise shut out every file next to the page, since the page is not served from there.
- Scripts are on by default; the choice (`html.scripts` in global state) applies to every open preview (`open` in the provider). Off means `script-src 'none'` in the policy and a `sandbox` without `allow-scripts` on the frame, which is what makes `<noscript>` show.
- The page in the frame is of the same origin as the webview page around it. That is what everything in `hook()` rests on: the listeners inside the frame are functions of the webview page, so nothing is injected into the previewed page and they work with its scripts off. `last()` moves a listener behind those of the page, so that it sees whether the page handled the event itself.
  - Clicks on links never navigate the frame. A link to a place on the page sets `location.hash` (with a `<base>`, the link itself would lead to the folder); anything else goes to the provider as `link`.
  - Forms are not submitted, except `method="dialog"`.
  - Keys: VS Code listens for the keys of a webview on the window of the webview page, which a key pressed in a frame inside it never reaches. `onKey()` repeats each key there as a synthetic event; VS Code takes those from extension webviews (`forwardUntrustedKeypressEvents`). Keys the page handled, and keys a script made up, are not passed on. The editing keys are carried out in the frame with `execCommand`, as VS Code does in its own frame; a `copy` command that reaches the webview page (VS Code's menu) is given the selection of the frame.
- The same origin also means a script of the previewed page can reach the toolbar page and post any message the provider accepts. Keep every message harmless under that assumption: none of them reads or writes a file, `link` only opens what it names in an editor or hands a web address to `openExternal` (where VS Code asks about untrusted domains), and nothing is written by name. What a page can reach is otherwise what a webview can: the network, and `localResourceRoots` (its folder and the workspace folder). Previewix declares no support for untrusted workspaces, so it does not run in Restricted Mode.
- A page that leaves (`onNavigate()`): the Navigation API's `navigate` event of the frame's window is cancelled for everything that would unload the document, which leaves the page as it is and tells the full address. A file is opened once per address (a redirect runs again with every keystroke in the source), or every time when the user has just clicked (`userActivation`: a button that sets `location`); a web address is only opened when the user asked. `location.reload()` and a navigation to the file itself write the page again (`again()`, at most `RELOADS` times in a row).
  - Behind that stands `frame-src 'self'` in the policy of the webview page: a frame that gets away is stopped there and left with an error page, and `lost()` says so. The violation report names only the origin, which is why this is not the main way.
- No flicker: a changed page loads in a second frame behind the one on screen (`pending`) and replaces it on `load`, or after `SWAP_AFTER`, at the old scroll position (`wanted`, kept until the page has loaded or the user scrolls). A `page` message with the text that is on screen (a save, a closed editor) leaves the page running, unless it says `force`.
- Files the page loads: a `PerformanceObserver` in the frame reports the resources from the folder's origin (`resources`), the provider watches their folders (one watcher per folder, `MAX_WATCHED`), and a change to one of them sends the page again with `force`. `fileOf()` in the provider turns an address of the page back into a file: same origin means same scheme and authority, so only the path is taken over.
- Links (`follow()` in the provider): a file opens with `vscode.open` in the editor VS Code has for it, a folder means its `index.html`, a missing file is a `note`; `http`, `https`, `mailto` and `tel` go to `openExternal`.
- **Width** sizes `#sheet`, which holds the frames, and scales it down as a whole when it is wider than the stage. The sheet is white, as a browser's canvas is: a page without a background of its own would otherwise show the editor's.
- Not there, by nature of the frame: addresses that begin with `/` (they lead to the root of the file system), a frame in the page that names another local page (a navigation is not served by the service worker), `alert()` and its like, popups and fullscreen (VS Code's sandbox for webviews).
- Limits: 32 MB (`MAX_BYTES`). State (`vscode.setState`): width and scroll position. No `retainContextWhenHidden`: a hidden page would go on running its scripts.
- `previewix.openHtmlPreview` (button in the text editor's title bar) leads back from the source. `introduceHtml()` in `associations.ts` tells those who had Previewix before it opened HTML files, once, at their first one.
- Run in a real VS Code 1.140 (see "By hand"): the frame's address, loading of stylesheets, pictures, scripts and `fetch` from the folder, reload on a change of the file and of a stylesheet, scripts off, the widths, links on the page, a missing file, and `Cmd+P` with the focus inside the page. Run only in headless Chrome: everything about pages that leave, the swap without flicker, the state after a rebuilt page. Not run anywhere: the tabs a link opens, **Open source** and the way back, **Open in browser**, the notification, and the editing keys through the macOS menu.

### PDF and Word (`documentViewer.ts`, `webview/pdf.js`, `webview/docx.js`)

- Both webviews fetch the file themselves from its webview URI. (A PDF restored from a backup is the exception: its bytes are sent in the `source` message.)
- pdf.js specifics:
  - `webview/pdfjs-global.js` must be imported before `pdfjs-dist/web/pdf_viewer.mjs`, which reads the core library from `globalThis.pdfjsLib` when evaluated.
  - The worker can't be started from a cross-origin extension URL. Its code is fetched and started from a blob URL; the CSP needs `worker-src blob:` and `'wasm-unsafe-eval'`.
  - `esbuild.js` copies the worker, `pdf_viewer.css`, images, cmaps, standard fonts, wasm decoders and ICC profiles into `dist/pdfjs/`. They are loaded at runtime from the `data-assets` base URL on `<body>`. The editing widgets need nothing beyond these: their icons and cursors are in `images/`, and their English strings are built into `pdf_viewer.mjs` (`GenericL10n` without a locale file).
- PDF messages to the webview: `source` (`src`, or `data` with `unsaved` for a backup; `dark`), `dark` `{on}`, `save` `{id, backup}`, `saved` `{id}`, `changedOnDisk`, `converted`. From the webview: `ready`, `loaded` `{signed}`, `edited`, `bytes` `{id, data | error}`, `requestSave`, `revert`, `dark` `{on}`, `openLink`, `saveMarkdown`.
- Annotating and form filling are pdf.js' own (`AnnotationEditorUIManager`, which `PDFViewer` creates for every document). The page only supplies the controls and translates between them and pdf.js' events:
  - A tool is `viewer.annotationEditorMode = {mode}`. pdf.js asks for one itself with `switchannotationeditormode` (a double click on an annotation of the file, selecting an annotation of another kind) and `showannotationeditorui` (its highlight button next to a text selection); both have to be answered, or those gestures do nothing.
  - The options bar (`#toolOptions`, one `data-tool` group per tool) sends `switchannotationeditorparams` `{type, value}` and mirrors `annotationeditorparamschanged`, which also reports the values of a selected annotation. `PARAMS` in `pdf.js` is the table of controls. Undo and redo are `editingaction`.
  - The image tool is pdf.js' stamp editor without its alt-text dialog (the button is hidden in `pdf.css`). Signatures and comments need manager objects and dialogs the page doesn't have, and scripting (`PDFScriptingManager` with its sandbox) is not set up.
  - The form fields are HTML inputs in pdf.js' annotation layer. `pdf.css` therefore scopes the page's own `button`/`input`/`select` rules to `#toolbar`, `#toolOptions`, `#notice` and `#password`; an unscoped rule would restyle the fields of the document and pdf.js' editing toolbars. Those toolbars get VS Code's colors through pdf.js' CSS variables (`--editor-toolbar-*`, `--outline-color`), and a `color-scheme` for what isn't overridden.
- Saving, and why the PDF is a `CustomEditorProvider` while everything else that edits here is not: the changes exist only in the page, and only a full custom editor gets the unsaved mark, `Ctrl/Cmd+S`, the question on close, Save As, revert and hot exit from VS Code. The rules:
  - Changes are reported as `CustomDocumentContentChangeEvent` (no undo steps: the history is pdf.js', inside the page). pdf.js' own "modified" flag is useless for this, since a radio group raises it while it is merely drawn, and only once. `edited()` is called from three wrapped `uiManager` methods (`addCommands`, `undo`, `redo`) and from `input`/`change` events in the annotation layer; the first call reports at once, later ones on a 400 ms debounce, to keep VS Code's backup fresh.
  - The provider never has the document. `bytesOf()` asks the page (`save` -> `pdf.saveDocument()` -> `bytes`), checks for `%PDF-` and only then writes. `saveDocument()` is an incremental update: the bytes that were loaded, plus the changed objects at the end. So an encrypted file stays encrypted, and the signed part of a signed file stays byte-identical.
  - A save finishes a note that is being typed; a backup never does, and a save that wasn't asked for inside the page within the last 5 s (auto save) doesn't either while the cursor is in a note. Committing it later reports a new change.
  - `saved` `{id}` names the request whose bytes were written. The page compares its edit counter with the one it noted for that request (`snapshots`) and answers `edited` if something changed in between, because VS Code has by then marked the document clean.
  - The file is written by `replaceFile()` (`tags/common.ts`): next to the original, then renamed. `document.saving` covers the watcher's echo, as in the audio editor.
  - `followFile` gets `keep: dirty || saving`. A change on disk reloads a clean document; for a dirty one the page shows a notice (`changedOnDisk`), and `confirmSave()` asks before overwriting. It also asks once per document before saving into a signed PDF (`IsSignaturesPresent` from `getMetadata()`).
  - A backup is the saved document written to the destination VS Code names. `document.backup` remembers it: it is what a restored session opens (`openContext.backupId`), what `bytesOf()` falls back to while no page is loaded (Save All on a restored tab that was never shown), and what a page gets if it is rebuilt while the document is dirty.
  - One editor per document (`supportsMultipleEditorsPerDocument` is off): two pages couldn't share unsaved changes. `retainContextWhenHidden` keeps them across tab switches.
- Thumbnails (`#thumbs`): a virtual list. Every page has a slot of the same height (from the shape of page 1; other shapes are fitted in), slots exist only around the scroll position, and one page at a time is rendered, nearest to the middle first, at 128 CSS px. Finished canvases stay in an LRU of 120. After each one `thumbnailrendered` is dispatched, which is pdf.js' own cue to free the page's data unless the viewer shows that page. `THUMB_LABEL` and `THUMB_GAP` in `pdf.js` repeat sizes from `pdf.css`. A rotation or a new document bumps `thumbEpoch`, which invalidates what is being drawn.
- Dark pages (`body.dark-pages`; the choice is in global state, `pdf.darkPages`, and a change is passed on to the other open PDFs):
  - The inversion is one element per page, `.canvasWrapper::after`, with `backdrop-filter: url(#night)`. It lies over the canvas and over pdf.js' draw layer (highlights, ink, the drawn selection) but under the text layer, so selection and find marks are untouched. `isolation: isolate` on the wrapper is what keeps it under the layers above; without it the pseudo-element's `z-index` puts it over the form fields and they are inverted twice.
  - `#night` is an SVG filter in the page: one color matrix (invert and turn the hue by 180° in one step, so nothing is clamped in between) and a gamma curve that maps white to #1a and lifts dark colors, which is what keeps a highlight visible. The annotation layer, a note being typed and the thumbnails are HTML outside the wrapper and get the same filter as `filter`.
  - Photographs: `findPhotos()` draws the page once more at 160 px with `recordImages`, after which pdf.js has the corners of every picture (`page.imageCoordinates`, fractions of the page). A picture counts as a photograph unless half of it or more is near white (that is a scan, a chart or a formula, which reads better inverted) or it is smaller than 24 pt. The photographs become holes in the layer: `--photos` on the wrapper is a mask image, an SVG with one polygon per picture, so turned pictures and overlaps come for free. The corners are turned with the page's rotation in `keepPhotos()`. Stencil masks aren't reported by pdf.js and stay inverted, which is right for the 1-bit scans that use them.
  - Why not a filter on the canvas with the photographs inverted back: a hue rotation leaves the RGB cube, so saturated colors can't be restored by a second pass. Cutting holes leaves the pixels alone.
- Word rendering is `docx-preview`. `fixBullets()` replaces Symbol/Wingdings private-use bullet characters, which browsers draw as empty boxes.
- Export to Markdown:
  - PDF: done in the webview (`pdfMarkdown.js`), because pdf.js already has the document open. It is heuristic: headings from font size, paragraphs from gaps and indents, list items from bullet characters and numbers. Tables, images and inline styles are not recovered.
  - DOCX: done in the extension (`docxMarkdown.ts`). Custom turndown rules close and reopen emphasis on every line (a Word run can span line breaks, Markdown emphasis can't), promote the first table row to a header, and map page breaks to line breaks. Images are written to `<name>_images/`.
  - The provider owns the save dialog, writes the files and opens the result.

### Fonts (`fontEditor.ts`, `fontInfo.ts`, `media/font.js`)

- Messages to the webview: `init` (file name, size, format and one entry per face: names, summary, character `ranges`, `blocks`, `axes`, `instances`, `features`, `css` descriptors, display-ready `sections`), `font` `{index, bytes}`, `error`. From the webview: `ready`, `face` `{index}`, `copy` `{text, what}`.
- Parsing is hand-written in `fontInfo.ts` and reads only what the page shows: `name`, `cmap`, `head`, `hhea`, `OS/2`, `post`, `maxp`, `fvar` and the feature lists of `GSUB`/`GPOS`. Glyph outlines are never parsed; the browser draws the font.
  - WOFF tables are inflated one by one. A WOFF2 file is one Brotli stream holding all tables; the transformed ones (`glyf`, `loca`, sometimes `hmtx`) are skipped because nothing reads them.
  - Each optional table is read inside `attempt()`, so a damaged table loses only its own rows.
- The webview loads the font with `new FontFace(name, bytes)`, which needs `font-src blob: data:` in the CSP. Browsers don't load collections, so `faceBytes()` copies the chosen face of a TTC/OTC into a standalone sfnt; other formats are passed through as they are. Fonts over 64 MB are not sent, and the page then shows the details without samples.
- Axes and features are applied through the `--variations` and `--features` custom properties on `<body>`, which every `.specimen` element uses. Specimens stay hidden until the face's font has loaded, so text never flashes in a fallback font.
- The CSS box is built in the webview by `renderCss()` from the face's `css` descriptors (`fontFaceDescriptors()` in `fontInfo.ts`: weight, style and stretch from `OS/2`, or ranges from the `wght`, `wdth` and `slnt` axes) and the current axis and feature settings.
- The character grid is drawn 600 cells at a time; CJK fonts have tens of thousands of characters.
- `unicodeBlocks.ts` is generated from Perl's Unicode data (`Unicode::UCD::charblocks`, Unicode 13). Characters outside every block there are grouped as "Other".

### SQLite (`sqliteEditor.ts`, `sqliteDb.ts`, `sqliteWorker.ts`, `sqliteHistory.ts`, `media/sqlite.js`)

- The engine is `node:sqlite`, the SQLite built into the Node.js runtime of VS Code. It needs no native module or wasm, reads WAL databases and locks like any other SQLite client. VS Code 1.103 (Node.js 22.17) is the first with everything the editor uses: 1.101 and 1.102 have the module without `setReturnArrays()` and `columns()`, and `sqliteWorker.ts` refuses to start there. On an older VS Code the worker fails to load the module. In both cases the editor says that it needs a newer VS Code.
- `node:sqlite` is synchronous, so every operation runs in a worker thread (`dist/sqliteWorker.js`, a second entry point of the extension bundle). Each editor starts its own worker on first use and terminates it when the tab closes. Long jobs (export, import) run in a worker of their own (`Database.run()`), so the page keeps browsing meanwhile.
- The webview drives everything through one generic pair of messages: `request` `{id, method, args}` and `response` `{id, result | error}`. Worker methods: `schema`, `count`, `rows`, `cell`, `save`, `query`, `blob`, `saveBlob`, `exportRows`, `csvPreview`, `importCsv`. Some requests are served by the provider because they need a dialog, a progress notification or the extension's storage (`own` in `resolveCustomEditor`): `export`, `pickCsv`, `csvPreview`, `import`, `saveBlob`, `history`, `remember`, `clearHistory`. The page never names a file to read: `pickCsv` keeps the chosen CSV path in the provider. The provider only adds `init` (answer to `ready`) and `changed` (file watcher, which also watches the `-wal` file because WAL writes don't touch the main file).
- Long jobs report through `Job`: the worker posts `{id, progress: {done, total}}` (at most every 100 ms) and reads cancellation from a `SharedArrayBuffer` flag sent with the request, because it reads no messages while it works. Closing the tab sets the flag instead of terminating the job, so an import rolls back cleanly.
- Each request opens the file, works and closes it; no connection is held. Reads use a read-only connection. `query` tries read-only first and reopens for writing only when SQLite answers `SQLITE_READONLY`; it then runs the whole script again from its beginning, since the first run can't have written. An export of a query result reruns it read-only, so it can never write.
- Values cross to the webview as `Wire`: integers outside the safe range as `{int}`, blobs as `{blob: size, hex: first 16 bytes}`, texts over 300 characters as `{text, more}`. The cut is made in the `SELECT` itself, so a page of large blobs is never loaded. `cell` fetches a full text when it is opened for editing.
- Rows are addressed by `rowid` (or `_rowid_` / `oid` when a column takes that name) or, for `WITHOUT ROWID` tables, by the primary key. Views and virtual tables have no key and are read-only.
- Edits are staged in the webview (`pending`, per table: updates, deletes, inserts) and written by `save` in one `BEGIN IMMEDIATE` transaction. An update or delete that doesn't hit exactly one row aborts the whole save.
- Typed text is converted by `parseInput()` according to the column's affinity; numbers travel as `{num: 'as typed'}` and are bound as integers when they are integers, because `node:sqlite` binds a JS number as a float. `sqliteDb.ts` has a copy of `parseInput()` for the CSV import (plus `X'…'` blob literals in typeless/BLOB columns); keep the two in step.
- Statements from the SQL prompt and CSV imports run immediately and are not part of the staged edits, which stay staged.
- Foreign keys: `describe()` adds `foreignKeys` to every table from `PRAGMA foreign_key_list`, with both sides under the columns' real names, a key without columns resolved to the other table's primary key, and `broken` set to the reason when the table or the columns aren't there.
  - Following is by value, not by row: `rows`, `exportRows` and a blob by position take `match` `{columns, values}`, which `scope()` turns into `column = ?` next to the filter. Comparing against the column applies its affinity and collation, which is how SQLite itself matches a key. That one mechanism serves keys to a rowid, to a unique column and to several columns, and the reverse direction (the rows that refer to a row) is the same request against the referring table.
  - The page asks for the target rows first and moves only when there are some, so a NULL or a dangling reference is reported in the bar (`#refs`) and never leaves an empty page behind. Values come from `cellValue()`, so a staged edit is followed as typed; a text the grid has only the beginning of is fetched with `cell`, a blob longer than the 16 bytes of `Wire` can't be followed.
  - `match` narrows the table on screen (`#trail` says how, with **Show all rows**), and `trail` holds the views left behind (table, page, sort, filter, match, cell, scroll) for **Back**. Opening a table from the sidebar clears both. Both are kept in `vscode.setState`.
  - Nothing is put into the cells: a click selects and a double-click edits as everywhere else. Following is `Ctrl/Cmd+click`, `Ctrl/Cmd+Enter` or the bar under the grid, which appears below the rows so that none of them moves under the pointer.
- Scripts: SQLite decides where a statement ends. `Script.next()` hands `db.prepare()` the text from where the last statement ended, and `sourceSQL` of the statement it gets back is exactly the text SQLite took, so strings, quoted names, comments and trigger bodies need no parser of ours. `skipBlank()` only steps over what may stand between two statements (blank space, comments, empty statements), because `prepare()` throws on a text without a statement. A long script is handed over in pieces (16 K characters, growing) to keep this linear; a statement counts only when SQLite ends it before the end of the piece.
  - There is no transaction around a script: each statement commits as SQLite does, and the script may use its own `BEGIN`/`COMMIT`. `query` stops at the first error and returns it in `error` `{index, message, sql}` with the outcomes of the statements before it, rather than throwing. A transaction left open (by an error or a missing `COMMIT`) is rolled back when the connection closes; `rolledBack` is the statement that began it, found with `isTransaction` (or a probing `BEGIN` where the runtime lacks it). The page turns this into the sentence about what stays.
  - `QueryResult` holds one `Outcome` per statement (`rows`, `changes` from `total_changes()`, `ms`) and the last result set. Its `source` `{sql, index}` is how that result is read again, for an export and for blobs: after a read-only run the script up to that statement (so a temporary table is there again), after a run that wrote only the statement itself, and `null` when the statement itself wrote. `resultStatement()` replays it on a read-only connection.
- History (`sqliteHistory.ts`): one JSON file per database in `<globalStorage>/sqlite-history/`, named by a hash of the document URI, read and rewritten (temp file and rename) on every change, so windows share it. 200 entries, 1 MB of SQL, entries over 100,000 characters are not kept, the histories of the 100 databases used last are kept. A script is one entry; the same text moves up instead of repeating; a failed run is marked `failed`. The page records with `remember` after every run and steps through the list with `recall()`.
- Completion is a list over the plain `<textarea>` (`completionsAt()` in `sqlite.js`), positioned by laying the text out in a hidden copy (`caretPoint()`). `scanSql()` is a rough tokenizer that only has to say where the caret is (in a word, a quoted name, a string, a comment) and which tables the statement around it names, aliases included. The rules that keep it out of the way: it opens by itself only while a word is typed (`insertText`) or after `table.`, never on a paste, a deletion or a caret move; `Tab` accepts; `Enter` accepts only after the arrows were used or the list was asked for (`Ctrl+Space`, `Alt+Esc`), otherwise it is a line break; any key with `Ctrl/Cmd` closes the list first, so Run still runs. Text is inserted with `execCommand('insertText')`, which keeps the textarea's undo. `RESERVED` lists the keywords SQLite won't take as a name unquoted.
- Export (`exportRows`) streams rows from the statement into a temp sibling file in 64 KB writes and renames it at the end. CSV: NULL empty, empty text `""`, reals via `realText()` (shortest round-trip digits, `.0` for integral values, `±9e999` for infinity), blobs `X'HEX'`. JSON: integers beyond ±2^53 as strings, blobs base64, duplicate column names suffixed `_2`.
- Import (`importCsv`) reads the file in 1 MB chunks through `CsvFile`/`readRow()`, which follow `parseCsv()` in `csv.ts` and also record whether a field was quoted (`""` is an empty text, an empty field is NULL). The encoding follows `decodeText()` (UTF-16 by BOM, Windows-1252 when the first chunk isn't valid UTF-8). A new table is created inside the same transaction. `csvPreview` reads the first 4 MB for the preview, header detection and type inference.
- Blobs: the webview recognises pictures from the `hex` prefix (`blobKind()`). `blob` sends a picture of up to 16 MB whole (shown through a blob URL, hence `img-src blob:` in the CSP), and otherwise the first 4096 bytes for the hex view. A blob is addressed by row key, by position in the sorted/filtered table (views), or by row and column in a rerun query result.

### Tables: CSV, JSON Lines, Excel, Parquet, dBase (`tableEditor.ts`, `csvEditor.ts`, `csvEdit.ts`, `csv.ts`, `jsonl.ts`, `xlsxRead.ts`, `parquetRead.ts`, `dbf.ts`, `media/table.js`)

- One page serves all five kinds; `data-kind` on `<body>` (`csv`, `jsonl`, `xlsx`, `parquet`, `dbf`) tells them apart, and `tableHtml()` leaves out of the HTML what a kind doesn't have (header checkbox, delimiter, encoding, **Open source**, export, everything for editing).
- Two providers show that page. `TableEditorProvider` is read-only and serves JSON Lines, spreadsheets, Parquet and dBase. `CsvEditorProvider` serves delimited text, which is edited: see "Editing delimited text" below.
- Messages to the webview: `file` (`load` number, name, size, `sheets`, or `error`; plus `delimiter`, `detected`, `encoding`, `editable`, `state` for CSV, `encoding`, `broken`, `firstBroken` for JSON Lines, `parquet` `{rows, totalRows, rowGroups, codecs, createdBy, warning}` for Parquet, `dbf` (the `DbfInfo`), `encodings`, `chosen` for dBase), `table` (`load`, `index`, `text` as UTF-8 bytes, `ends`, `rowEnds`; plus `nums` and `merges` for spreadsheets, `names` and `lines` for JSON Lines, `names`, `types`, `details`, `numeric` for Parquet and dBase, `version` for CSV), `exported`. From the webview: `ready` `{delimiter, encoding}`, `delimiter` `{value}`, `encoding` `{value}`, `sheet` `{load, index}`, `export` `{index}`, `openSource` `{line?}`, `copy` `{text, what}`.
- A table is a `FlatTable` (`csv.ts`): all cell texts as one string, `ends` with the end offset of every cell, `rowEnds` with the number of cells up to the end of every row. Rows may differ in length. This is what makes 200,000 × 30 workable: a `string[][]` of six million strings costs several times the memory and has to pass through JSON on its way to the webview, while the text as bytes and two typed arrays are transferred as they are.
- The whole table lives in the webview, which sorts, filters, counts and draws it without asking the provider. Measured on 200,000 × 30 (52 MB of CSV): about 1 s to parse in the extension host; 35 to 120 ms for the row filter, depending on how many rows match; 40 to 90 ms for a sort; 5 to 22 ms for a column filter; 15 to 35 ms for the statistics of a whole column.
- Column names: in CSV and spreadsheets they are row 0 of the table while **First row is header** is on (`first()` is then 1). JSON Lines, Parquet and dBase send them as `names`, and the table holds data rows only. `label(c)` is the one place that knows the difference.
- JSON Lines, Parquet and dBase keep nothing: every load (first, file change, another code page) reads and parses the file again. The spreadsheet provider keeps the flat sheets of the last load, sends one when the page asks (`sheet`), and exports from them. The CSV document keeps the bytes of the file, and parses them for every page it sends the table to.
- `load` numbers the reads of the file. A `table` or `sheet` message with an old number is dropped, which is what keeps a slow read from overwriting a newer one.
- Readers that take seconds run in a worker thread: `startWorker()` starts `dist/<name>` with `workerData`, takes the one message it posts (the result, or `error`) and terminates it. A newer load and the closing of the tab stop the reader that is at work. `xlsxRead.ts`, `jsonl.ts`, `parquetRead.ts` and `dbf.ts` are entries of the extension bundle for this, and each starts working when it finds its key in `workerData` (`previewixSheets`, `previewixJsonLines`, `previewixParquet`, `previewixDbf`); `csvEdit.ts` is one too (`previewixCsv`), for writing. Without the bundle, spreadsheets, JSON Lines and dBase are read in the extension host; Parquet has no such fallback, so hyparquet is not bundled twice. CSV is still parsed in the extension host. The Parquet reader is started with `WATCHED`: its heap is limited (2 GB, twice what the largest table shown was seen to take), it posts `{alive: true}` every second from a timer, and `startWorker()` stops it and tells the user when it has been silent for 20 seconds, which a reader caught in a loop is and one waiting for a slow disk is not.
- Limits (`MAX_BYTES`): 100 MB for delimited text and JSON Lines, 50 MB for spreadsheets, 256 MB for a dBase file (and for its memo file), and for a Parquet file that isn't on a local disk. Larger files get a message instead of a table.

Numbers, statistics, filters and copying (`media/table.js`):

- `numberAt(i, c)` is the only place that decides whether a cell is a number, and sorting, right alignment, the statistics, the number filters and JSON copying all go through it: `nums` for a spreadsheet, the `numeric` flag of the column for Parquet, and the `NUMBER` pattern for text (so `007` is a number and `1,234` is not).
- `order` holds the table rows on screen after filter and sort, or `null` for all rows in file order. The selection (`anchor`, `active`) is in rows as shown; `fileRow(d)` maps one to its row in the table. `rebuild()` works `order` out again and drops the selection.
- The row filter lower-cases one whole row at a time and then confirms the hit inside a single cell, since a match across two cells doesn't count. Column filters (`filters`, by column index) are tested first, one cell each; `isComplete()` says whether a filter can be applied yet, and one that can't (a comparison without a number) is kept but ignored.
- `countSelection()` runs from `updateStatus()` whenever the selection changes. It works for `STATS_SLICE` (8 ms) at a time and continues from a timer, and a newer selection drops the run (`statsRun`): a column of 200,000 cells is done in about 30 ms, six million cells in under 300 ms without a pause longer than a frame. The sum is compensated (Neumaier), so `0.1 + 0.2` shows as 0.3.
- `selectionText(format)` builds all four copy formats. Markdown escapes the backslash, the pipe, the asterisk, the backtick, `[`, `<`, entities, and the underscores that aren't inside a word, and writes a line break as `<br>`; JSON writes a number with the digits of the cell (`JSON_NUMBER`), so nothing is rounded; CSV follows `csvField()` in `csv.ts`. `MAX_COPY_CELLS` (2,000,000) applies to every format, because the text goes through the provider to the clipboard in one message.
- The popups (`#copyMenu`, `#columnFilter`, and `#columnMenu` of delimited text) are `position: fixed` and closed by a press anywhere else and by a new table, the filter also by a horizontal scroll.
- A click on a column header is told from `e.target`, or from what lies under the pointer when a redraw between the press and the release has replaced the element that was pressed.

The grid:

- It is not a `<table>`: rows and cells are absolutely positioned `div`s, and `draw()` rebuilds only the rows and columns in the window (plus 8 rows of overscan) on every scroll frame. The header and the row numbers are `position: sticky`. Row and header heights are fixed and repeated in `table.css`.
- Past 30 million pixels (1.25 million rows) the scrolled area is capped and the scroll position is mapped to rows at a scale (`virtualTop()`); `pinned` keeps keyboard navigation exact there.
- Column widths come from the header (with the type, where there is one) and the longest cell among the first 500 rows, measured in a hidden `.ruler` element rather than a canvas, because number cells use tabular figures.
- Merged ranges are drawn as one cell laid over the cells they cover, only while `order` is `null`.

Editing delimited text (`csvEditor.ts`, `csvEdit.ts`, and "Editing" in `media/table.js`):

- `previewix.csv` is a full `CustomEditorProvider` with a document model of its own, so that VS Code knows of unsaved edits: the dirty dot, save, save as, revert, the question on closing, backups for hot exit, and undo and redo through `onDidChangeCustomDocument`. Staging edits in the page, as the SQLite viewer does, would lose them silently when the tab is closed. A `CustomTextEditorProvider`, as Markdown uses, would end at VS Code's 50 MB limit for extensions, decode the file by VS Code's setting instead of this viewer's detection, and hold the text twice.
- Who holds what:
  - The page holds the table and applies every edit to it at once.
  - The document (`CsvDocument`) holds the bytes of the file as read or as last written (`bytes`, and `print`, their SHA-256), and the undo history as steps (`log`, with `index` of them applied).
  - The table as it stands is always "the file plus `path()`", which is what a save writes, a backup stores and a new page is sent (`editedTable()`). Nothing depends on a page being alive.
  - `editable` in the `file` message switches editing on in the page. It is off for a file that is too large or unreadable, and for a file system that can't be written to (`isWritableFileSystem()`), such as the older side of a comparison.
- An edit is a list of steps (`Op` in `csvEdit.ts`), and every step is about rows, numbered as the table stands at that moment, rising:
  - `set` gives rows new cells: all of them, or with `at` in the place of cells from that column on (as many as come, or `widths[k]` of them, which is how a column goes in or out).
  - `insert` adds rows, `delete` takes rows out.
  - Rows travel as a `FlatTable` with the text as UTF-8 bytes, so a paste of 10,000 cells is three typed arrays.
- The page applies a step by building `text`, `ends` and `rowEnds` anew in one pass (`spliceRows()`, `spliceCells()`), so every loop that reads them stays as it is; that pass returns what it replaced, which makes the inverse step. `commit()` posts `edit` `{version, label, ops, inverse}`. The provider keeps both, tells VS Code (`undo` and `redo` of the event post `ops` `{from, ops, step}` to every page of the document), and hands the steps to the other pages. A page applies only steps whose `from` is its own `version`; otherwise it asks for the table (`reload`). An `edit` with another `version` than the document's is answered with the table, as is one whose rows don't fit (`rowsAfter()`).
- Undoing past a save and then editing cuts the saved state out of the history. `detour` then holds the steps from the file to the state at `anchor`, and a plain content change is fired next to the edit, because VS Code only counts steps and would call the document saved again once the count matched.
- Rows as shown (`order`) are kept in step by `orderInsert()` and `orderDelete()`: a new row is shown where it was asked for (`before`), or, for a step from the provider, below the row it follows in the file. An edit never sorts or filters again; `stale` shows **Sort and filter again**, which is `rebuild()`.
- Writing (`render()`): the file is parsed with the place of every field (`parseCsvSpans()`), the steps are replayed over it as a `Model`, and the result is put together from ranges of the file, copied as bytes, and new text.
  - A row is the number of an untouched row or a list of cells, and a cell is a cell of the file (a number) or a new text. A cell that is set to the text it has stays a cell of the file. That is where "untouched fields keep their bytes" is decided.
  - A new text is quoted when it holds the delimiter, a quote or a line break, and also where that is the way of the file: the field it replaces was quoted without need, or every field of the file is quoted (`fresh()`).
  - A row keeps its own line break; a new row gets the one most rows have (`commonBreak()`), or the system's in a file without any. A file that ends without a line break goes on ending without one.
  - Three places where a field can't be copied as it is: a quoted field that is never closed and a field that ends with half a UTF-16 character can only stand at the very end (`pinned`); a row of one empty cell is written as `""` at the end of a file without a final line break and between a lone carriage return and a line feed.
  - Offsets in the decoded text become offsets in the bytes by `byteOffsets()`; new text is encoded by `encode()`, which collects the characters Windows-1252 has no place for instead of writing something else (`Unencodable`).
  - With `verify` the result is decoded and parsed again and compared with `Model.table()`; a save never writes bytes that fail this. It also catches bytes that only became valid UTF-8 through an edit, which would change how the file is read.
  - Above 1 MB this runs in a worker thread (`dist/csvEdit.js`): about 1 s for one edit in 54 MB, about 3 s for many.
- Saving (`saveCustomDocument()`):
  - The file on disk is read and its fingerprint compared with `print`; a newer file is overwritten only after a modal question. The same comparison is what makes the watcher ignore the extension's own write, and what `changedOnDisk` and the note in the page come from.
  - A dirty `TextDocument` on the same file is asked about too (`textDirty`), and **Open source** with unsaved edits offers to save first: the table and a text editor are two working copies, and neither may overwrite the other silently.
  - `Unencodable` leads to the question whether to write the whole file as UTF-8, with or without a byte order mark (`convert`).
  - The file is written next to the target and renamed (`replaceFile()`), at the place a symbolic link points to.
  - `keep` of `followFile()` is "unsaved edits, or a write under way", so a file that is deleted under unsaved edits gets no placeholder, and a save writes it anew.
  - VS Code takes the document for saved as it stands when the save returns, so an edit that arrived meanwhile is written in another round.
- Reloading from disk (a change without unsaved edits, **Revert File** when the file is another one, a new delimiter) starts a new `generation`: the steps VS Code still holds do nothing then. The delimiter can't be changed while there are unsaved edits, and stays the one the edits were made with (`used`) even if a save changes what `detectDelimiter()` finds.
- A backup (`packBackup()`) is the bytes of the file and the steps of `path()`, not a rendered file: restoring gives the same document, the question about the encoding included, and the file on disk may have changed meanwhile without the edits being lost.
- In the page: `openEditor()` puts a `<textarea>` over the cell (`placeEditor()` keeps it there while the grid scrolls). It stops `Ctrl/Cmd+Z` from reaching VS Code, which would undo the last edit of the table instead of the typing. A double click is the second `mousedown` (`e.detail`), since the first has redrawn the rows. Typing opens the editor from `keydown` and lets the key land in it. A paste is the `paste` event; if none follows `Ctrl/Cmd+V`, the clipboard is read through the provider (`readClipboard`). `lastCopy` lets a paste of this table's own copy keep cells that only look quoted.
- Measured on 200,000 × 30 (54 MB), in the page: a cell 15 to 30 ms, a paste of 1,000 × 10 cells 30 ms, a value pasted into a whole column 150 ms, a row inserted or deleted 20 to 30 ms, 10,000 rows deleted 45 ms, a column inserted or deleted 50 to 100 ms; an undo or redo of any of them 20 to 45 ms.

The formats:

- Text encoding (CSV and JSON Lines): UTF-16 by byte order mark, otherwise UTF-8, and Windows-1252 when the bytes aren't valid UTF-8.
- `previewix.openCsvPreview` (button in the text editor's title bar) leads back from the source of both text kinds; `TableEditorProvider.textViewType()` picks the view type by the extension.
- `jsonl.ts`: columns are the keys in order of first appearance, so the names are known only at the end and are sent apart from the rows. An array fills the columns `1`, `2`, …; any other value goes to `value`. A line with a run of 16 digits is parsed with the source text at hand (`JSON.parse` with a reviver and `JSON.rawJSON`), so integers beyond 2^53 keep their digits; the rest take the fast path. A line that fails is counted, the first 20 are reported with their line numbers, and `lines` gives the line of every row once a line was skipped. `JSON.parse` lists the keys that look like whole numbers first, whatever their place in the line, so an object that has one gets its keys from `writtenKeys()`, which reads them off the text.
- `xlsxRead.ts` reads with SheetJS in `dense` mode and takes each cell's formatted text (`w`). `nums` holds the raw number of numeric cells (a date is its serial number) for alignment and sorting. Rows end at their last value and empty rows at the end are dropped, so a stray cell far out doesn't produce a huge table. Reading a workbook is synchronous and slow (about 6 s and 700 MB for 46 MB).
- Numbers files: SheetJS reads the values but not the number formats, and gives a date as a count of days from 1904 with the format `m/d/yy`. `numbersText()` writes such a date as ISO and a number with its own digits; formatting them as Excel cells put every date four years off. Every table of a sheet is a sheet of the workbook.
- `dbf.ts` reads dBase tables itself. SheetJS reads them too, but its bundle has no code page tables (`cpexcel`), so text outside ASCII came out garbled, dates stayed `19870301`, long numbers turned into `1.23457E+17`, memo fields were placeholders, and a file with bytes after its end marker was refused.
  - Headers of dBase III, IV and 7 (68-byte header, 48-byte field descriptors), FoxPro and Visual FoxPro; dBase II is refused. The record count of the header is only a hint: whole records are read up to the end marker or the end of the file, so a file that was cut off shows what is there, with `info.warning`. Limits as for Parquet: `MAX_ROWS`, `MAX_CELLS`, `MAX_CHARS`.
  - Cells are text made in the reader: N and F as the stored digits (never through a float), D as ISO, L as `true` / `false`, I, Y (exact, by BigInt), T, B and O; M from the memo file (`openMemo()`: dBase III blocks up to 0x1A, dBase IV blocks with a length, FoxPro `.fpt` with big-endian headers), `(memo)` without one, `(binary)` for pictures and objects. `_NullFlags` of Visual FoxPro is not a column; it gives the nulls and the length of varchar fields. `numeric` marks N, F, I, Y, B as double and O. Rows have every column, unlike the other readers'.
  - Code page (`choosePage()`): the user's choice, then the `.cpg` file, then the language driver byte at offset 29 (`DRIVERS`), then a guess (`guessPage()`: UTF-8 when valid with a multi-byte sequence, CP866 or Windows-1251 when the high bytes are runs from their Cyrillic ranges, CP850 when a byte occurs that Windows-1252 leaves undefined, otherwise Windows-1252). `info.encodingSource` says which, and the status line repeats it. `TextDecoder` knows only the WHATWG encodings, so the DOS pages (437, 850, 852, 855, 857, 860 to 863, 865, 737, 775) and Mac Central European and Greek are 128-character tables in the file, generated from Python's codecs. Kamenický (895) and Mazovia (620) are not there.
  - For a single-byte code page the records are decoded once into a string with one character per byte, and a field is a slice of it; only multi-byte pages decode field by field. A million records of ten fields (100 MB) take about half a second.
  - The provider finds what lies next to the table (`besideDbf()`): a file of the same name with `.dbt` or `.fpt`, and one with `.cpg`, in any case. They are read on every load, but not watched: a change to the memo file alone shows up when the table is reloaded.
  - The page gets `encodings` (`DBF_ENCODINGS`) for the **Encoding** select, which posts `encoding` `{value}`; the choice is kept in the webview state and comes back with `ready`.
- `parquetRead.ts`: hyparquet reads one row group at a time into `FlatBuilder`, up to `MAX_ROWS` (1,000,000), `MAX_CELLS` (10 million) and `MAX_CHARS` (128 MB of text). A file on disk is read in parts, without holding up the thread, so only the footer and the row groups shown are touched; another file system hands over the whole file as bytes.
  - hyparquet trusts the file, and a damaged one could make it loop for good, take gigabytes or leave a promise to fail on its own. So it never reads from the file. `parquetGuard.ts` checks the footer first: its bytes (`checkThrift()`: every list and structure ends inside it, since hyparquet's own Thrift reader stops at the end of the bytes without a word and makes a list as long as the file claims; at most 16 MB), then what it says (`checkFooter()`: the schema adds up, every column chunk names a column of the schema and lies inside the file), with the marking of GeoParquet columns switched off until that is done. Then, for each row group, `checkedColumns()` reads the bytes of every column and walks its pages (`checkChunk()`): the header, the sizes, the number of values, and what a decoder would take on trust, which is the length of every run of levels and dictionary indexes, the shape of delta blocks, and the lengths of delta-coded texts. hyparquet gets a stand-in file that holds the checked bytes and zeros elsewhere. A column that fails is left empty and named, as one that hyparquet can't read is.
  - The page checks follow hyparquet's own reading step by step (they have to stop where it stops), and unpack every page a second time, which costs 2 to 9 % of a read. They belong to the pinned version: after raising it, read `readColumn()`, `readDataPage()`, `readDataPageV2()`, `readRleBitPackedHybrid()` and `deltaByteArray()` there again, and run the damaged-file pass of the tests with more files.
  - Limits of a page: 256 MB unpacked, 16,777,216 values; of a nested column in one row group, 67 million values.
  - Compression: gzip, Brotli and Zstandard come from `zlib` of the runtime (Zstandard since Node 22.15, which is VS Code 1.101), with `maxOutputLength` set to the size the page declares; Snappy and LZ4 are written out in the file (`snappy()`, `lz4Block()`, and `lz4Hadoop()` for the framing of the older codec). hyparquet's own Snappy decoder is not used: on damaged data it can take a length below zero, step back in its input and go round for seconds or for good. No compression package is bundled.
  - Values become text in the worker: `columnFormat()` picks the formatter of a top-level column from its schema. `withoutConversions()` strips the annotation of top-level decimals (hyparquet would make floats of them) and of intervals and BSON (which it refuses), so they arrive as stored. Dates and timestamps are formatted by `parsers`, at any depth. `utf8: false` leaves binary without an annotation as bytes, which are shown as text when they are valid UTF-8 and in hex otherwise.
  - When a row group can't be read at once, `columnsApart()` reads it column by column, leaves the failing ones empty and names them in `warning`. Known cases in hyparquet 1.31.1 and 1.31.3: `DELTA_BYTE_ARRAY` in a version 1 data page, and plain-encoded nested columns in version 2 data pages. The package is pinned to an exact version (1.31.1); run the comparison with `pyarrow` again when it is raised.
  - Errors of our own are `Refusal`s and are shown as they are; anything else is wrapped in "the file is damaged, or written in a way Previewix does not read". A damaged file always ends in a table, a refusal or that sentence: the tests read 1,200 damaged copies in a process with 256 MB of heap, and the provider's watch over the worker (above) is the last line behind the checks.

### Archives (`archiveEditor.ts`, `src/archive/`, `media/archive.js`)

- Messages to the webview: `listing` (name, format, archive size, optional `warning`, `locked` when the names were encrypted, and `entries` as arrays `[path, kind, size, packed, mtime, blocked, link, encrypted]`, kind 0 file / 1 folder / 2 link, packed -1 when unknown), `locked` `{name}` (the list of files needs a password), `error`. From the webview: `ready`, `open` `{index}`, `extract` `{path?}` (no path means everything), `unlock`. Indexes refer to the listing the provider sent last.
- `archive/index.ts` is the only module the provider imports: `listArchive()`, `extractFile()`, `extractEntries()`, `countExisting()`, `createZip()`, `freeName()`, `PasswordError`, `maybeWrongPassword()`. The format is told from the content (`packingOf()` for gzip, bzip2, xz and Zstandard, the 7z and RAR signatures, a valid tar header checksum, otherwise ZIP), never from the extension.
- Modules of `src/archive/`: `common.ts` (types, `cleanPath()`, `safeSegments()`, CRC-32, `PasswordError`), `zip.ts`, `tar.ts`, `sevenZip.ts`, `rar.ts`, the decoders `lzma.ts` (LZMA and LZMA2), `xz.ts`, `bzip2.ts`, `inflate.ts` (Deflate and Deflate64), `filters.ts` (branch filters, Delta, BCJ2), `stream.ts` (what the decoders are built from), `worker.ts` and `host.ts` (the worker thread and the host's end of it), `zipWrite.ts`.
- The decoders are hand-written and synchronous: each is an `Input` (`read()` returns the next piece or undefined) that pulls from another one, down to `fileInput()`, which reads a file descriptor. A chain can't wait for I/O, which is why it runs in a worker. `Arena` hands working memory (probability tables, windows) from one decoder to the next; without it an archive of 70,000 small files leaves a gigabyte of buffers for the garbage collector.
- The worker (`dist/archiveWorker.js`, an entry of the extension bundle; `src/archiveWorker.ts` only imports `archive/worker.ts`) does one job and is terminated: a listing (7z, RAR, tar.bz2, tar.xz) or a run over entries (those, and a ZIP run that includes an entry `isHeavy()`: Deflate64, bzip2, LZMA, XZ). Plain tar, tar.gz, tar.zst and ordinary ZIP entries stay in the extension host, on zlib's own threads.
  - A worker never writes a file. It posts `{begin: index}`, the data as `Uint8Array`s (copies, transferred), `{end: error | null}`, and at last `{done}` or `{fail}`; `runJob()` in `host.ts` turns that into the same `Visitor` calls the host's readers make, so `extractFile()` and `extractEntries()` don't know the difference.
  - The decoders never return to the event loop, so flow control is a `SharedArrayBuffer`: the host counts the pieces it has taken, the worker blocks in `Atomics.wait` while 16 are under way. A second counter names the entry whose rest isn't wanted.
  - Cancelling terminates the worker. So does closing the tab while a listing runs (`listArchive()` takes a signal).
- ZIP (`zip.ts`): only the end records and the central directory are read to list. ZIP64 end record and extra field; a stub in front of the archive shifts every offset. An entry's data is located through its local header and checked against the size and CRC of the directory, which is also the most that is ever unpacked.
  - Stored and Deflate go through `zlib.createInflateRaw()`, Zstandard through `zlib.createZstdDecompress()` where Node has it (22.15); Deflate64, bzip2, LZMA and XZ through the decoders above, over a descriptor of their own.
  - Names: UTF-8 when flagged or when the bytes are well-formed UTF-8, then the Info-ZIP Unicode path field (only if its checksum matches the plain name), otherwise CP437 or CP866. The code page is chosen once per archive by `looksCyrillic()`: Russian words are runs of bytes from the Cyrillic ranges, accented Latin letters stand alone.
  - Encryption: `zipCrypto()` (the classic one; the last byte of the 12-byte header must be the high byte of the CRC, or of the time when a data descriptor is used, and both are accepted) and `winZipAes()` (AE-1 and AE-2: PBKDF2-SHA1 with 1000 rounds, a two-byte check value, HMAC-SHA1 over the encrypted data, and AES in counter mode with a little-endian counter, which OpenSSL has no mode for, so the key stream is made with AES-ECB). AE-2 has no CRC; the HMAC stands in. PKWARE's strong encryption is `blocked`.
  - PPMd and the methods older than Deflate get `blocked` with the reason and are listed.
- tar (`tar.ts`): a `Source` is read forward only. A plain tar is read from the file and jumps over data, so listing touches only headers, and each entry's data offset is kept for direct extraction. A packed one (`Listing.packing`) is unpacked from the start for the listing and for every extraction. ustar prefix, GNU `L`/`K` long names, pax `path`, `linkpath`, `size`, `mtime`; binary size fields. Sparse files and devices are `blocked`.
  - A tar has no checksum for file content. bzip2 blocks are verified before any of their bytes leave `bzip2.ts`. gzip, xz and Zstandard are verified at the end of the stream or block, so the listing reads on to the very end (`Source.drain()`) and turns a mismatch into the `warning` of the listing, and an extraction that reaches the last entry does the same and throws.
- 7z (`sevenZip.ts`): the start header, the header (usually packed, and encrypted when names are: an "encoded header" is a folder of its own), folders with their coders and bind pairs, substreams, file properties. `openFolder()` builds the chain from the content end back to the packed streams; every coder's output is cut at its declared size (`capped()`).
  - A file is reached by unpacking what lies before it in its folder, so a run over entries goes folder by folder and stops after the last wanted file of each.
  - Coders: Copy, LZMA, LZMA2, bzip2, Deflate, Deflate64, AES, BCJ2, and the filters of `filters.ts`. A folder with anything else (PPMd, Zstandard and the other 7-Zip-zstd codecs, IA-64, RISC-V) marks its files `blocked`.
  - AES: SHA-256 over salt, password (UTF-16LE) and a counter, 2^n times; the key is cached per salt and password, because a non-solid archive has a folder per file. There is no check value: a decoder that fails on the first bytes of an encrypted folder is reported as a wrong password, anything later as `orPassword()` ("…, or the password is wrong").
  - Limits: 256 MB of header, a dictionary of 1.5 GB (`MAX_WINDOW` in `lzma.ts`; the window is never larger than the declared output), 2^24 hashing rounds.
- RAR (`rar.ts`): UnRAR compiled to WebAssembly, from the `node-unrar-js` package. Only its Emscripten module is used (`node-unrar-js/dist/js/unrar`, typed in `unrar.d.ts`; `esbuild.js` copies `unrar.wasm` to `dist/`), not its wrapper, which unpacks to memory or writes files itself. `withArchive()` gives UnRAR the seven file callbacks it asks for: reads are served from the archive and from files in the same folder (further volumes), and `create` never creates anything, the data goes to the `Sink`. Output past the declared size is refused.
  - `RARProcessFile` runs to the end of a file synchronously and can't be interrupted; cancelling terminates the worker.
  - The module's header exposes less than the format has: no link targets, no redirection type. Links are recognised by their attributes and listed without a target; a hard link or a "file copy" entry unpacks to nothing and is reported as such.
  - In extract mode UnRAR also returns the header of a file that began in an earlier volume, in list mode it doesn't; `walk()` skips it so that entry numbers agree. Archives of RAR 1.5 and 2.0 end without an end mark, which UnRAR reports as damage; `atEnd()` tells that apart.
  - The Emscripten glue installs `uncaughtException` and `unhandledRejection` handlers that rethrow. That is harmless in the worker and one more reason not to load it in the extension host: `index.ts` must not import `rar.ts`.
- Passwords: an entry that needs one has `encrypted`; a listing whose names were encrypted has `locked`. `PasswordError` (`wrong` false: missing, true: doesn't fit) is the only way a password problem is reported; it crosses the worker boundary by name. `extractEntries()` tries the password on up to three encrypted entries first (`checkPassword()`, a run with `probe`), so a wrong one is noticed before anything is written and one entry damaged in the wrong place doesn't lock out the rest. The provider keeps the password in a variable of the panel's closure, asks with `showInputBox({password: true})`, and asks again on `PasswordError` (`withPassword()`, `unlock()`). It is never stored and never logged.
- Paths: `cleanPath()` turns a stored name into the listed path (backslashes become separators, leading slashes and drive letters are dropped) and marks a name with `..` as unsafe, which blocks the entry. Extraction does not rely on that: `targetOf()` re-checks every segment with `safeSegments()` and compares the resolved path with the target folder. Keep both. No reader chooses where a file goes: UnRAR's own idea of a file name is ignored.
- Links are listed and never created, so no later entry can be written through one.
- Every file is written as `<name>.<pid>-<random>.part` next to its target and renamed, so a wrong checksum, a cancel or a full disk leaves nothing under the final name.
- Opening a file extracts it to `<globalStorage>/archive/<pid>-<id>/<panel>/<n>/<entry name>` (the name picks the editor), makes it read-only and runs `vscode.open` with `preview: false`, because the archive tab is usually a preview tab itself and would be replaced. The panel's folder is removed on dispose. Global storage is shared between windows, so the first use removes only the session folders whose process is gone.
- The provider keeps the listing and re-sends it on `ready`; only a change on disk reads the archive again.
- The page builds the tree once, sorts a folder's children when it is first shown, and draws only the rows in view (`ROW` in `archive.js` must match the row height in `archive.css`). Under a filter, folders that lead to a match are open, and a folder that matches itself shows all of its content.
- "Compress to ZIP" (`previewix.compressToZip`, `explorer/context`; `compressToZip()` in `archiveEditor.ts`, `createZip()` in `zipWrite.ts`): VS Code passes the clicked item and the selection. The archive goes next to the clicked item as `<name>.zip`, or `Archive.zip` for several, under a free name (`freeName()`), written as a `.part` sibling and renamed.
  - No data descriptors: a large file's header is written with zeros, the data streamed through `zlib.createDeflateRaw()`, and the header written again with the real sizes and CRC. Room for 64-bit sizes is reserved up front for files from `ZIP64_FROM` on. An entry that fails halfway is cut off again (`Output.rewind()`) and reported as skipped.
  - Files under 256 KB are read into one shared buffer and deflated in one go, with a window and an output buffer sized to the file (`smallOptions()`), and stored when Deflate doesn't make them smaller. With zlib's defaults, 70,000 small files left 1.2 GB of buffers behind.
  - Names are NFC with the UTF-8 flag; "made by Unix" with the mode in the external attributes, plus the DOS directory bit; the UTC time in an extended-timestamp field next to the DOS time. Symbolic links are stored as links (`lstat`, never followed); devices, pipes and sockets are skipped. A ZIP64 end record is written only when a count, a size or an offset needs it.

### Choosing file types (`associations.ts`)

- A custom editor's priority is fixed in `package.json`, so the only way to step aside for a file type at runtime is the user's `workbench.editorAssociations` setting. `previewix.chooseFileTypes` shows one checkbox per viewer and writes that setting.
- The list of viewers and their extensions is read from `contributes.customEditors` of the extension's own `package.json` (`viewersOf()`), so a new viewer appears without being listed again. Association keys are lower case: VS Code matches them without regard to case.
- Only viewers whose state changes are touched (`withChoice()`). Switching one off gives each extension to VS Code's own viewer where it accepts that extension (`BUILT_IN`) and to the text editor (`default`) otherwise. Switching it on deletes the entries, whatever editor they named.
- A viewer counts as off only when every one of its extensions is associated with another editor, so a single `*.csv` entry the user made by hand leaves the Table viewer checked and untouched.
- The setting is written to the workspace when the workspace already has a value for it (it would hide the user's), otherwise to the user settings.
- The first activation shows the command once in a notification (`previewix.introduced` in global state), because taking over Markdown, CSV and SVG surprises people who wanted the text.

## Conventions

- TypeScript in `src/` is strict. Webview code is plain JavaScript with `// @ts-check` and JSDoc casts where needed.
- User-facing strings are English.
- Comments explain why, not what. Match the existing density.
- Use the shared helpers: `getNonce()`, `parentOf()`, `watchFile()`, `followFile()`, `missingAssets()` in `util.ts`; `findFfmpeg()` in `ffmpeg.ts`; `textDecoder()` in `textDecoding.ts`.
- Node.js 22.17, which VS Code 1.103 runs on, and the releases right after it have two traps that the tests cover (run the suite with such a binary first on the PATH when touching either):
  - `new TextDecoder('windows-1252')` reads the page as Latin-1 there (through Node.js 22.20), so the euro sign, curly quotes and dashes come out as control characters. Decode legacy text with `textDecoder()`, never with the constructor.
  - `node:sqlite` there (through 22.19) answers "column index out of range" to a numbered parameter such as `?1`. Bind with plain `?`.
- New npm dependencies must bundle with esbuild, because the extension is packaged with `--no-dependencies` and ships no `node_modules`.
  - `mediainfo.js` is aliased to its CJS build in `esbuild.js`; the ESM builds rely on `import.meta`.
  - Runtime assets (wasm, fonts) are copied into `dist/` by `copyAssets()` and located through `context.extensionPath` or a webview URI.
- `localResourceRoots` must include every folder a webview loads from: `media/`, `dist/` where needed, and the document's folder.
- ffmpeg is optional and used for the audio waveform, for tags of Ogg, Opus and AIFF (and of the MP4 files the native backend declines), and in the video player for saving a clip by stream copy and for reading text subtitle tracks out of the file. It is never used to make a file playable. Without it the features that need it are left out of the page (no waveform, no tag section, no clip button, no tracks from inside the video) rather than shown with an error. The `previewix.ffmpegPath` setting overrides the lookup.
- Bump `version` in `package.json` for every packaged build.

## Verifying changes

### The test suite

`npm test` runs the regression tests in `test/` with Node's own test runner (`node:test`, `node:assert`); it needs no build and no dependency of its own, and takes a few seconds. Run it before and after any change to a module it covers, and add a test with every fix there.

- `test/run.js` bundles every `test/*.test.ts` with esbuild, one bundle per file, into a temporary folder that also gets what the code under test looks for beside its own bundle (`archiveWorker.js`, `sqliteWorker.js`, `unrar.wasm`, as in `dist/`), and runs them with `node --test`. `vscode` is aliased to the empty `test/vscode.ts`, so a module that imports it only for its command or provider half can still be loaded.
  - `node test/run.js tags csvEdit` runs the files whose names contain one of the words; options go on to `node --test` (`--test-name-pattern=symbolic`).
  - Tests are TypeScript, import from `src/` directly, and are type-checked by `npm run typecheck` (`test/tsconfig.json`).
  - A test runs as a bundle in the temporary folder: use `root` and `fixture()` of `test/helpers.ts` for files of the project, never `__dirname` (which is right only for the worker entries beside the bundle).
- It has to pass on Node.js 22.17 (the oldest VS Code the SQLite viewer supports) and on what VS Code ships now, whose `crypto` (BoringSSL), SQLite and zlib differ from plain Node: `ELECTRON_RUN_AS_NODE=1 "<VS Code binary>" test/run.js`. Run both after a change to anything that uses `node:sqlite`, `crypto` or `zlib`. Where a runtime itself is wrong (Node.js 22.13 to 22.20 and 24.0 decode `windows-1252` as Latin-1, 22.17 to 22.19 don't bind a value to `?1`), the tests that show it are `todo` on that runtime only, with the reason (`latin1Runtime` in `test/helpers.ts`).
- What it covers, by file:
  - `tagsMp3`, `tagsFlac`, `tagsWav`, `tagsMp4`, `tags`: `src/tags/`. Every file is built by hand (`test/audio.ts`), and what a save wrote is taken apart by readers in that file which share no code with the writers: the audio byte range, every chunk of every MP4 track through the chunk offsets and sample tables, and the bytes of every frame, block, chunk and item that was not edited. `tags` holds what `index.ts` decides (also a save through a symbolic link) and the checks against ffmpeg, ffprobe and mutagen.
  - `csvEdit`: `render()` and what surrounds it in `src/csvEdit.ts`. Named cases spell out the expected file; a randomised pass with a tokenizer of its own checks that every field, line break and byte order mark that was not edited keeps its bytes.
  - `archive`, `archiveFormats`, `zipWrite`: `src/archive/`. Hostile names in ZIP, tar, 7z and RAR archives built by hand (`test/archives.ts`), links, sizes and checksums that lie, damage; every decoder against the small archives in `test/fixtures/archive/`; "Compress to ZIP" read back by a strict ZIP reader of the tests' own.
  - `markdownEdit`, `markdownRender`, `htmlPage`, `sqlite`, `sqliteImport`, `sqliteHistory`, `csv`, `jsonl`, `xlsx`, `parquet`, `dbf`, `cert`, `certSecrets`, `subtitles`, `associations`, `font`, `imageMeta`, `imageFormats`, `tiff`, `psd`: the modules of those names. `certSecrets` searches the whole output of `parseCertFile()` for the private numbers of the test keys.
- What it does not cover: the providers, the webview pages in `media/` and `webview/`, and everything that needs VS Code or a browser (custom editor registration, dialogs, the clipboard, saving a PDF, drawing and color management of pictures). Also left out: `videoTools.ts` (saving a clip), `mediaInfo.ts`, `docxMarkdown.ts`, and what only shows with very large files (ZIP64, an MP4 whose offsets pass 4 GiB, a decoder's memory use). Those are verified the way the rest of this section describes.
- Writing tests:
  - Build the input in the test where a few lines can; hand-built bytes are best, because the test then decides what the file says. Commit a file to `test/fixtures/<area>/` only when nothing in Node can write it, next to the script or the note that says how it was made.
  - For code that rewrites users' files, check the result with something that shares no code with the writer, and compare the file before and after for everything the edit should not touch.
  - A program that not every machine has (ffmpeg, ffprobe, Python with mutagen or pyarrow, openssl, sips, unzip) may only add a second opinion: such a test skips with the reason (`needs()`, `which()`, `python()` in `helpers.ts`; `PREVIEWIX_TEST_PYTHON` names the interpreter to try first), and the core of every area runs without any of them.
  - Where the value is in randomness, use `random(seed)` with a fixed seed and keep the pass short.
  - A reader that may never return on damaged input can't be stopped from inside the process: such a case runs in a child process with a time limit (`parquet.test.ts` and `tiff.test.ts` start their own bundle again for it).
  - A test that shows a bug nobody has fixed yet stays in the suite with `{ todo: 'the reason' }`: the run stays green and prints it with a ⚠. `node test/run.js 2>&1 | grep '⚠'` is the list of known bugs; fixing one means removing its `todo`.

### By hand

Nothing in the repository runs the extension inside VS Code automatically. What the test suite doesn't reach was verified outside VS Code so far, and each approach is easy to recreate:

- Webview pages: load the provider's HTML body in headless Chrome (for example with `puppeteer-core` and the installed Chrome), with a stub `acquireVsCodeApi` that records posted messages, then drive the page and post the provider's messages by hand. For PDF and DOCX, serve the page and the resources from two different local origins to mimic the webview's cross-origin setup and CSP.
- PDF annotating and saving: run the real `PdfEditorProvider` in Node against a stand-in for the `vscode` module (bundle `documentViewer.ts` with `vscode` external and resolve it to the stand-in), with its page in headless Chrome, and pass the messages between the two; that covers save, Save As, revert, backup and restore, and the questions before a save. Drive the tools with real mouse and key events. Start Chrome with `--screen-info={1728x1117}`: headless reports a 400 x 300 screen, and pdf.js sizes its canvases by the screen. Fixtures: `reportlab` for an AcroForm, `pypdf` for annotations and encryption. Check a saved file with `pypdf`, and check that it begins with the bytes of the original.
- Extension-host modules without a `vscode` import (`markdownRender.ts`, `markdownEdit.ts`, `htmlPage.ts`, `docxMarkdown.ts`, `fontInfo.ts`, `certInfo.ts`, `sqliteDb.ts`, `sqliteHistory.ts`, `csv.ts`, `csvEdit.ts`, `jsonl.ts`, `xlsxRead.ts`, `parquetRead.ts`, `dbf.ts`, `imageMeta.ts`, `src/imageFormats/*`, `subtitles.ts`, `videoTools.ts`, `src/archive/*`, `src/tags/*`) can be bundled with esbuild and called from Node directly. The test suite does exactly that, so a new check of such a module belongs there, as a test, rather than in a script of its own.
- Markdown: bundle `markdownEditor.ts` with `vscode` left external and resolve it to a small stand-in (a `TextDocument` that changes only through `workspace.applyEdit`, `WorkspaceEdit`, `Range`, `Uri`), run the real provider on it, serve its HTML from one local origin and `media/` and `dist/` from another, and connect the two: the page's `postMessage` to the provider's handler, the provider's to the page. Edits are then made by typing into the page and checked in the document's text. Record `securitypolicyviolation` events; Mermaid and the KaTeX fonts only load if the CSP lets them. To see a page before Mermaid arrives, delay the files under `dist/mermaid/`. VS Code's theme is classes on `<body>` (`vscode-light`, `vscode-dark`, `vscode-high-contrast`, plus `vscode-high-contrast-light`) and `--vscode-*` variables on `<html>`.
- HTML: serve the provider's page (its `<body>` with a stub `acquireVsCodeApi`) and an empty `fake.html` from one local origin, with `?id=…` in the page's address so that the frame is made as in VS Code, and the test site from another; post `page` messages built with the real `preparePage()` and `pagePolicy()`. Cases: a page with a stylesheet, a script, `fetch` and a subfolder; a redirect in the head, a script that sets `location` by itself and from a button, one that reloads itself, `pushState`; a page that handles clicks and keys on its window; scripts off; an empty file. Keys and the clicks that have to count as the user's need real input events (CDP `Input.dispatch…`) and the page in front.
- A real VS Code can be driven from outside: start its binary with `--extensionDevelopmentPath=<project>`, `--remote-debugging-port=<port>`, `--user-data-dir` and `--extensions-dir` of the test's own, `--disable-workspace-trust`, a folder and a file, and attach to the targets it lists over CDP. The webview is a target of its own (`vscode-webview://…`); its page is `iframe#active-frame` inside it, of the same origin. Three things to know: the user data folder needs a short path (VS Code puts a socket in it, 103 characters at most); a shell started from an editor's extension host carries `ELECTRON_RUN_AS_NODE` and `VSCODE_*`, which have to go (`env -i` with `HOME`, `PATH`, `TMPDIR`); and it opens a window on the owner's screen, so say so first and keep it short.
- Fonts: the system font folders cover every case (`.ttf`, variable fonts, `.ttc` with TrueType and with CFF outlines); WOFF and WOFF2 files ship inside VS Code and other apps. Load the webview page with the provider's CSP in place, since the font loading depends on it.
- Certificates: generate the cases with `openssl` (RSA, ECDSA, Ed25519; a CA, an intermediate and a leaf with names of every kind; expired, not yet valid, ending soon; chains in right, reversed and mixed order; DER, PKCS #7; encrypted and plain keys in PKCS #1, PKCS #8, SEC 1 and OpenSSH form; a request) and compare every field with `openssl x509 -text`, as for the 128 real certificates in `/etc/ssl/cert.pem`. Run the same script under VS Code's runtime (`ELECTRON_RUN_AS_NODE=1 <VS Code binary> script.js`), because what can be verified differs there. Cut a DER file at every length and flip bytes: nothing may throw. After any change to `certInfo.ts`, run `node test/run.js cert`: `certSecrets` searches the result for the private numbers of the test keys and for the challenge password (as hex and as Base64 in all three alignments, which is how a secret travels inside a PEM), with keys under every label, inside wrappings, put into certificates, and cut at every byte. A new way of handing bytes back needs a test there that plants a secret in it.
- SQLite: run `dist/sqliteWorker.js` as a worker under VS Code's own runtime (`ELECTRON_RUN_AS_NODE=1 <VS Code binary> script.js`) to test against the SQLite version that ships. For the webview, expose `sqliteDb.ts` to the headless page and answer its `request` messages from it (and the history requests from `sqliteHistory.ts`). Test databases should include WAL mode, a `WITHOUT ROWID` table, a `STRICT` table, a view, blobs, long texts and 64-bit integers, and foreign keys of every kind: single, composite, to a unique column that is not the rowid, self-referencing, NULL, dangling, and to a missing table. Scripts should be tried with semicolons in strings, quoted names and comments, a trigger, statements that end exactly at the end of a 16 K piece, a failure in the middle with and without the script's own `BEGIN`, and `RESERVED` checked by using every keyword as a column name. For export and import, round-trip a table through CSV into a new table and compare with `EXCEPT` both ways, including `typeof()` per column.
- Archives: bundle `src/archive/index.ts` and `src/archiveWorker.ts` into one folder, copy `unrar.wasm` next to them, and call the first from Node, and under VS Code's runtime too, since Zstandard and the worker depend on it. Build test archives with `zip` (also `-0`, `-e`, `-y`), `ditto`, `bsdtar` (`--format ustar`, `gnutar`, `pax`, `7zip`; `-z`, `-j`, `-J`, `--zstd`; `--no-mac-metadata`) and Python's `zipfile`/`tarfile`: ZIP64 (over 65,535 entries, an entry over 4 GiB of zeros), names in CP866 and CP437 without the UTF-8 flag, bzip2 and LZMA entries, a flipped data byte, truncated files, and hostile names (`../`, absolute, drive letters, backslashes, a symlink with a file "inside" it). Extract and compare with `diff -r`, and check that nothing appears outside the target folder.
  - The `7z-wasm` package (7-Zip itself; install it outside the project, it is a test tool only) writes what the system tools can't: 7z with any method and filter, solid or not, `-p` and `-mhe=on`, ZIP with `-mem=AES256` or `ZipCrypto` and `-mm=LZMA`, `BZip2`, `Deflate64`, `xz`. It also unpacks RAR, which makes it the oracle for `rar.ts`. It can't write BCJ2 (no threads); 7-Zip's own releases (`7z2409-extra.7z`, `lzma2409.7z`) are packed with it.
  - Nothing here can make a RAR archive. The test files of the Python package `rarfile` cover RAR 1.5 to 5, solid, volumes, passwords, encrypted headers, links and Unicode names, all small. A RAR 5 archive of stored files is easy to write by hand (vint fields, CRC-32 per header), which is enough for hostile names, sizes that lie and an entry over 4 GiB.
  - The decoders: compare with `xz -dc` and `bzip2 -dc` over empty, one-byte, random, zero, text, binary and run-heavy inputs, every `xz` filter (`--x86`, `--arm64`, `--delta`…), every check type, `-T` (several blocks), concatenated streams, and `lc`/`lp`/`pb` settings.
  - Damage: cut the archive at several places, flip a byte at several places, zero a stretch; list and extract each variant, and compare every file that was written with the original. Bombs: sizes that lie in both directions (a 7z with the Copy or LZMA coder is easy to write by hand), a dictionary of 4 GiB, a count of files no header could hold; watch the peak memory.
  - "Compress to ZIP": check the result with `unzip -t`, `zipinfo -v`, Python's `zipfile` and `ditto -x -k` (what Finder's Archive Utility runs), extract and `diff -r --no-dereference`; 70,000 small files and a sparse file over 4 GiB; unreadable files, a pipe, a cancel halfway.
- Image formats: the decoders in `src/imageFormats/` run under Node (libheif too: `require` its `libheif-wasm/libheif.js` and pass `wasmBinary`), so pixels can be compared there; the color path and ICO only exist in a browser, so run `previewixImages.decode()` in headless Chrome as well, with the page on one origin, `dist/` on another and the editor's policy in a `<meta>` tag, and read the canvas back. For the editor itself, bundle `imageEditor.ts` with `vscode` resolved to a stub and connect the real provider to the page.
  - Fixtures: `sips -s format heic|tiff|psd|icns|ico` (`-s formatOptions lzw`), `heif-enc` (`--cut-tiles`, `--rotate-cw`, `-b 10`, `-L`, the nclx options, `-S` for a sequence; a JPEG with an EXIF orientation as input gives the iPhone combination of `irot` and EXIF), ImageMagick for every TIFF layout (`-compress`, `-define tiff:tile-geometry`, `-interlace plane`, `-define tiff:alpha=associated`, `-depth`, `-colorspace CMYK|Lab|Gray`, several inputs for pages, `TIFF64:` for BigTIFF) and for PSD modes, `iconutil -c icns` for an icon with every size. Photoshop's own files, with every mode, depth and kind of transparency, are in the tests of the `psd-tools` project. Icons with ARGB, packed RGB, JPEG 2000 and dark variants are in `/System/Library/CoreServices` and inside older applications.
  - References: `sips -s format png` gives the stored values, and `sips --matchTo` the sRGB profile gives what a color-managed viewer shows, which is what the canvas must hold for a file with a profile. ImageMagick (`-auto-orient`), `heif-convert`, `psd-tools` and `iconutil -c iconset` are second opinions. They disagree in instructive ways: `sips` does not un-blend the white under a Photoshop picture with transparency and, reading a PSD it wrote itself, hands out colors multiplied by the alpha, ImageMagick ignores CMYK profiles, `iconutil` un-multiplies ARGB entries that are straight. Decide by the source picture where there is one. A picture with transparency read back from a canvas differs from its source at low alpha (the canvas keeps colors multiplied), exactly as a PNG does.
  - HEIC from libheif differs from Apple's decoder by about one level on average and much more on single pixels along saturated edges (chroma upsampling); a lossless or 4:4:4 file must match exactly.
  - Damage: cut each format at several lengths, flip bits in the header and in the data, keep the magic and replace the rest by noise; for TIFF also a directory chain that loops, a tag with a count of 4 billion and strips outside the file; a PSD with the flag of resource 1057 cleared. Run every file in a process of its own with a time limit: the result must be a picture or a `DecodeError`, never a hang or another exception.
  - Mutate as well: take a sound TIFF of every compression (the fax ones and JPEG included, which the test suite has no packer for), overwrite bytes of the data, values of tags and whole tag values with extremes (0, 16384, 65535, 4 billion), decode a few hundred of each in a child process that reports before and after every file, and kill the child when it goes silent. Record the time and the growth of memory per file: a small picture that takes a second or a hundred megabytes is a bound that is missing. Label 1-bit noise and a megabyte of 0 and of 1 bits as each fax coding. The deadline of the page is tried with a worker script that spins forever, with and without announcing a size.
- Comparing images: bundle `imageCompare.ts` and `imageEditor.ts` together with `vscode` resolved to a stand-in whose `createWebviewPanel()` hands out panels the test can attach a headless page to, whose file watcher is a real one, and whose pickers and dialogs are scripted. Check every count and changed area against a computation that shares no code with the page: ImageMagick to raw RGBA and a loop of its own, over the same alignment and tolerances. For JPEG and HEIC, feed that loop the pixels as Chromium and libheif decode them (`previewixImages.decode()` on a plain page, written out as PNG), since other decoders differ by a level here and there. Cases: identical, one pixel, a moved region, a crop from a corner, from the middle and from an odd offset, the same picture at 2×, transparency (also colors hidden behind alpha 0), a re-saved JPEG across tolerances, an animation, 1 × 1, and files that can't be shown. For Git, give the stand-in a fake of the extension's API over a real repository; for the diff editor, panels whose `visible` and `viewColumn` the test sets. Measure two 48-megapixel pictures: the longest gap of a 4 ms timer on the page, the frame times of a drag in every mode, and the memory of the renderer process. A page in a background tab of headless Chrome does not answer clicks: bring it to the front first.
- Tables: bundle `tableEditor.ts` with `vscode` aliased to a stub module and run the real provider under Node against the page in headless Chrome, with the worker bundles in a `dist/` next to it; typed arrays have to be carried to the page in base64 pieces. Measure on a 200,000 × 30 CSV. Check the copy formats by reading them back (a CSV parser, `JSON.parse`, a Markdown renderer with HTML on) against cells with pipes, quotes, line breaks, backslashes and markup. For Parquet, write fixtures with `pyarrow` (every type, nulls, nested columns, each codec, data page version 2, the delta encodings, several row groups, more rows than are shown) and compare every cell with what `pyarrow` reads back; real `.numbers` files are in the test data of the `numbers-parser` project, which also gives the values to compare with. For dBase, write fixtures with Python's `dbf` package and by hand (the Visual FoxPro types, dBase IV and 7, cut and damaged files), compare every cell with `dbfread`, the code page tables with Python's codecs, and read every file cut at every length.
- Editing of delimited text:
  - The save path alone: bundle `csvEdit.ts` and call `render()` from Node with random steps on generated files (the four delimiters; CRLF, LF, CR and mixed; with and without a final line break; UTF-8 with and without BOM, UTF-16 LE and BE, Windows-1252; quoted fields with delimiters, quotes and line breaks, text behind a closing quote, a quote that is never closed; ragged rows; an empty file; half a UTF-16 character at the end). Check with a tokenizer of the test's own that the result parses to the edited table and that every field, line break and byte order mark that was not edited has its bytes. Run it under VS Code's runtime too.
  - The whole: bundle `csvEditor.ts` with `vscode` aliased to a stand-in and play VS Code's part for the custom document, which is short enough to copy from `MainThreadCustomEditorModel` in VS Code's `workbench.desktop.main.js`: a stack of edit events with a current and a saved index, `undo()` and `redo()` that call the event's functions, `save`, `revert` and `backup` that call the provider. Drive the page with a real mouse and keyboard, and carry typed arrays both ways (base64 in pieces). Keep headless Chrome from throttling the pages that aren't in front when two editors share a document.
  - Random actions through the page, then: a second editor on the document shows the same table (the provider's replay against the page's), undoing everything shows the first table, redoing shows the edited one, and the saved file opened anew shows it again.
- 3D models: bundle `modelEditor.ts` with `vscode` resolved to a stub and let the real provider answer the page's messages; serve its HTML from one local origin and the extension's files and the model's folder from another, so that the policy and the cross-origin loading are the real ones. Headless Chrome has WebGL with `--use-angle=swiftshader --enable-unsafe-swiftshader` (software) or `--use-angle=metal` (the GPU, on a Mac). Before the page loads, wrap `requestAnimationFrame` and the WebGL draw calls to prove that an idle model draws nothing, and the `create…`/`delete…` calls to see that a reload gives its buffers and textures back. Lose the context with the `WEBGL_lose_context` extension. The Khronos glTF-Sample-Assets repository has Draco, meshopt and KTX2 variants; look at the screenshots, since a model that loads can still be black, unframed or lying on its side.
- Video: Chrome decodes H.264 and VP9 with Opus or Vorbis, so generate test files with those (`testsrc2` with a sweep or noise as sound, since a plain sine makes identical audio packets; a known keyframe interval; one at 24000/1001 fps; a long 4K one for the seek preview; an MKV with several audio and subtitle tracks and an attachment; an MP4 with MPEG-4 Part 2 video for a picture that can't be decoded). The provider can be run for real: bundle `videoEditor.ts` with `vscode` external, resolve that to a stand-in (file access through `fs`, scripted dialogs, a `withProgress` that can cancel), and pass messages between it and the headless page, with the video served from a second origin with range requests. Check A–B boundaries by recording `currentTime` on every animation frame and at every seek the page makes. Check clips with ffprobe: duration, streams, and per-packet hashes (`-show_data_hash md5`), which must be an unbroken run of the source's packets starting at the chosen keyframe.
- Tag writing: generate tagged files with ffmpeg and `mutagen`, run read, no-op save, full edit, clear and cover operations, then check the result with `mutagen` and compare decoded-audio MD5 before and after. `npm test` does the core of this without any tool (see above) and the ffmpeg, ffprobe and mutagen part where they are installed; a change in `src/tags/` must not ship with any of that skipped, since it rewrites users' music files.
  - MP4 needs more than that, because a save can move the audio: AAC and ALAC, `moov` at the end and in front (`-movflags +faststart`), chapters (`.m4b`), two audio tracks, and files tagged with `mutagen` (freeform atoms, two covers, non-Latin text). Craft the layouts ffmpeg doesn't write by patching atoms: no `udta`, a `udta` with the zero terminator, a `meta` without `ilst`, no padding, a top-level `free` behind `moov`, `mdat` with size 0 and with a 64-bit size, a numeric `gnre`. After every write compare, with a parser that is not `mp4.ts`, the SHA of every `mdat` payload and of every whole chunk read through `stco`/`co64` (chunk sizes from `stsc` and `stsz`), next to `mutagen`, `ffprobe -v error` and the decoded MD5.
  - For the `stco` overflow, put a sparse `free` atom of nearly 4 GiB in front of `moov` (write the header, seek, write the rest) and shift the offsets, so that the last chunk sits just under 2^32; the file takes no disk space until it is rewritten.
  - Cut files at random offsets, at every atom boundary and inside `moov`: every cut must come out read-only with and without ffmpeg, and a save must fail with the file unchanged. mutagen can't open a file whose `udta` ends in the zero terminator or whose `meta` has no version and flags; check those with ffprobe.
  - Break the writer on purpose (an offset one byte off, a size not updated, an item dropped) and see that both `verify()` and the outside checks notice.

What these checks don't cover is the VS Code side: custom editor registration, save and open dialogs, Zen Mode fullscreen, clipboard, and `openWith` behavior. Verify those by hand with `F5` and say so when you couldn't.
